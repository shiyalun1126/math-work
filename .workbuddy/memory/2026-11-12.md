## 三元方程组"做不了"的真实原因（不是求解，是解析入口）

用户贴图 `x+y=6, y+z=8, x+z=10`（带题号 1) 和 left{...right. 的 aligned），页面报做不了。
求解层其实早就能算：同样的三条方程写成标准 cases，0.04s 出 x=4,y=2,z=6，7 步。

**根因链**：
1. VLM 两个模型都读对了，只是格式不同——qwen3-vl 输出 `\left\{\begin{aligned}...`，
   glm-4.6v 输出带行末逗号的 `\begin{cases}...`。
2. `latex.parse` 两种都吃不下 → `verify` 四个候选全判"无法解析"
   → `verdict=failed, confidence=0.0`。
3. `equations.answer` 硬用 `chosen` 去算，`extract` 把 aligned 整串又包了一层 cases，
   得到畸形 LaTeX，parse 失败 → 判"无解"，但 topic 说 coverage=in。
4. `parse('1)\left\{\begin{aligned}x+y&=6')` 还返回 **ok=True**，
   obj=`[(1, 6)]`——把题号的 1 和右边的 6 配成了 `1=6`。假成功，最难查。

**修法**：`latex.py` 新增 `canonical_env()`，在 `parse()` 入口调用。
把 aligned/alignedat/array/split/gathered/cases 统一捋成标准 cases：
剥题号 → 按 `\\` 拆行 → 去对齐符 `&` → 去行末逗号句号 → 重组。
凑不出两条就原样返回（单条方程、集合写法都不动）。

两个必须记住的坑：
- 题号判据必须带分隔标点并加 `(?!\d)`。只写 `^\d+` 会把 `2x+3=5` 剥成 `x+3=5`，
  `2.5x` 的小数点会被当成分隔点。
- 剥 `\left\{` 只在确定要重组时发生（靠整串替换实现），否则集合 `\left\{ x|x>0 \right\}`
  会被削掉一半。

**修后**：`verdict=ok, conf=1.0, "4/4 个候选语义一致"`；图片链路出 x=4,y=2,z=6 七步。
`CACHE_VERSION` 升 v5（解析层变了，题面归一结果变，旧缓存必须失效）。
新增 `tests/test_latex_env.py` 8 例。测试 258 passed。

## 齐次方程：按用户要求先不做，但已加的"防冤判"保留

上一轮发现：学生用课本的"设 y=kx"解齐次式，整条正确过程被判 wrong（从第 2 行起全线报错），
因为 `workcheck` 没有任何处理设元行的代码，`y=kx` 被当成普通等式去和题面比。
这违反项目原则"识别有把握才判错"。

已加的最小保护（用户选"先止血"，不加齐次求解能力）：
- `_DECLARE_LEAD` 认设元引导词，`_mark_declares()` 只认**引入题面没有的符号**的行
  （`设 x=2` 只是给原变量赋值，不误伤）。
- 设元行与其后含新符号的行一律 `unknown`（待确认），不参与推导链、不更新基准、不记 first_err。

- headline 分开说两件事："换回原变量后的结论成立；设元那一段（第 N 步起）没有验算"。
  只说"过程逐行成立"是假的。
- 结果：同一段过程从 wrong 变成 pass；`k` 算错（k=1→y=x）仍能抓成 wrong。

## 新增配方法推导（mathagent/derive.py）

用户要「ax²+bx+c=0 这种推导式」。原有 `params.discuss()` 只给六支结论，回答不了"求根公式怎么来的"。

新模块 `derive.complete_square(lhs, rhs)`：七步（原式 → 除二次项系数 → 移项 → 配料 → 完全平方 → 开方 → 求根公式）。

关键设计：
- **每一步都要验**。前五步查「相邻两步是同一方程乘一个不含主元的因子」（比例里出现主元就说明解集变了，不输出）；开方不是恒等变形，改验两支根代回原方程。验不过就不给推导。
- **只对二次项系数含字母的方程出推导**。数字系数（x²-5x+6=0）硬套模板会出现「两边除以 1」空转和 `- -5 ± √1` 双负号，直接返回 None。
- 标题走纯文本渲染（`_steps_md` 里是 `**标题**`），**标题里不能放 LaTeX 命令**，会原样显示。
- `4a²`、`2a` 不要 expand，否则 `(a+1)` 的系数会被摊成 `4a²+8a+4`，丢了结构。
- `_disc_latex` 用过 `evaluate=False` 强行排成 b²-4ac，结果 m 系数会印出 `\left(-4\right) m 1 + 4` —— 已回退成 sympy 默认输出，与 params 判别式一致。

接入：`Answer.derivation`、缓存存 derivation + note（CACHE_VERSION v7）、`app_student.py::_derive_md` 与 `app_equation.py::_derive_md` 各渲染一章「求根公式怎么推出来的」。

顺带修：覆盖条把参数也叫「未知数」（"未知数 a、b、c、x"），新增 `equations.vars_text()` 区分「未知数 x · 参数 a、b、c」。

测试：`tests/test_derive.py` 8 例，全量 275 passed。服务 7862（PID 39568）已带新代码重启。

## 拍照批改「识别不出来」：切行丢了 3 行（二元一次方程组）

用户贴一张手写方程组解答（`2x+y=4 ① / x+3y=7 ② … ∴{x=1,y=2}`），报"为什么识别不出来"。

**根因不在识别，在切行**：原图 10 个逻辑行，只切出 6 行，`⇒ y=2`、`x=1`、`∴{x=1,y=2}` 三块整段消失。切行少行**不报错**，看起来就像学生只写了一半，比切错行更难查。

三层修复（`mathagent/lines.py`、`mathagent/photocheck.py`）：

1. **`_fill_gaps` 补洞**（核心）。`_candidate_bands` 阈值是整页 `percentile(p,80)=50.8`，它默认每行墨迹同一水平。实拍不成立——后三块峰值只有 20~51（字小、笔画轻），整段被判"不是字"。改为：在"空档明显大于正常行距"处用局部阈值补找。
   - 局部阈值用 `percentile(seg,90)` 不用 `max`：空档里压着纸边（峰值 193.7，是正文 3 倍），拿 max 当基准阈值顶到 67.8，真正的字一个都过不去。
   - **补洞必须放在合并之后**。放前面会把中位行距带歪（W17 从 86 px 掉到 9.5 px），「正文块」聚类把 4 行拆成 5 块，最后只剩 3 条碎片。
   - 补出的带要剔**横向满幅**的：作业本格线抹不干净，低阈值下正好成带。不过滤时 fixture 4 行被补成 16 条等距"行"。
   - 空档两端各留 `0.25*med_h`：紧贴边界的是相邻带的下伸笔画（W08 最后一行的 `3` 下沿）。

2. **`lead_fragment_end` 裁行首括号残片**。`{` 横跨两行，水平投影从中间切开，两半各自混进相邻两行，被读成 `2`/`1`/`)`/`7`：`2x+y=4`→`22x+y=4`、`x+3y=7`→`1x+3y=7`、`y=2`→`7y=2`（后者被判"不成立"，学生明明写对了）。判据两条同时成立：宽 < 0.6*行高（残片 9~15 px）**且** 间隙 >= 1.2*宽（真 `1x` 里 1 和 x 只差 2~5 px）。
   - 安全阀 `gap <= 1.2*band_h`：没有它，第一块是纸面噪点时会把左边一大片空白裁掉，W04 的「有」、W08 的「x=」就是这么整行退化成"读不出算式"的。
   - 最多连跳两块（末尾常是「∴ { y=2」，推导符和括号残片并排）。

3. **行尾编号剥离**（`_TAIL_MARK`）。`③-①得：5y=10 ④` 的编号让 `parse()` 失败，于是 `_tiebreak_by_math`（按"哪个接得上邻行"裁决两派识别）静默失效——两个来源明明都读出了能对账的式子，却裁不动。剥 `①②`、`\textcircled{}`、`\tag{}`、行尾 `(4)`（`(?<=\s)` 限定，否则 `x=2(3)` 的乘 3 会被剥）。**必须在 `\text{}` 剥完之后**，否则末尾还是 `}` 够不着。
   - 顺带：`_neighbor` 原来返回原始 latex（带 `\text{②}`），同解判断必然失败，改成返回 `text`。

**结果**：10 行全在，7 行认准（第 1、5、10 行标待核对），整份判 unread 而不是假结论。八页 W01~W17 切行数全部不变。

## 手动补识别（识别失败的行由人改，再判）

用户提法：识别要尽量全，但允许某几行识别失败，失败的行可以手动输入正确式子让系统评判过程。

**做法**：把「判定」从「识别」里拆出来（`photocheck._judge`）。识别只产出 `lines`，判定可以反复做：
`regrade(pc, text, confirm=...)` 不调模型，几百毫秒重算。

界面（`app_student.py` 批改页）：结果下面多一块「有行没认准？」——预填 `1. 2x+y=4` 这种带**原行号**的文本
（`edit_text`），改完点「按我改的重新判」。行号只用于对齐（`workcheck._ENUM` 会剥），
用户删了行号则退回按位置对应。

**三条规则（这是要害，别改松）**：
- 改过的行 → `ok`/conf 1.0/来源 `手输`，结论里点名（系统没核对原件，不能把用户的判断算自己的功劳）
- 没改但勾了「核对」→ 同样确定，来源 `核对`
- **没改也没勾 → 保持原来的把握，窟窿还是窟窿**

第三条的来历：`y=2` 被读成 `7y=2`，用户只改别的行、这行原样留着，若当成他写的，
接下来判的「不成立」全是冤案——"允许修改"的入口反而成了新的冤枉来源。所以默认不确认，
要确认单独勾。勾选项由 `_doubt_choices` 生成（只列 `not sure` 的行）。

**顺手修的三处**：
- `app_student._assign_cell` 原来按空格拆，`y = 2` 显示成「y，=，2」；现在只认 `\quad`/逗号/分号/「或」
- `workcheck._grade_linear_system` 的 `res.expected` 改用 `_is_point()` 把关：题面只填了第一行时
  解出来是 `x = 2 - y/2, y = y`，印在「标准答案」后面像没看懂题。现在欠定就不给标准答案。
- `res.got` 去重：`x=1` 抄两行时结论写「y=2、x=1、x=1」，像系统把一行数成两行

## R01 超时改成可终止（子进程）

验收报告 R01：超时不可取消——`join(timeout)` 只停止等待，sympy 还在跑且握着 GIL，
20 次超时后 20 个后台线程存活。线程杀不掉（`PyThreadState_SetAsyncExc` 只作用于
字节码之间，simplify 多在 C 层），只能换进程。

- 新增 `mathagent/guard.py`（父端）+ `mathagent/_worker.py`（子端）：常驻 worker，
  二进制长度前缀 + pickle，一次一件事。超时 = `kill`，下次用时重启（~1s）。
  子进程中途崩（OOM/段错误）只重启不复算。
- 子进程用 `-m mathagent._worker` 起，**不用 multiprocessing**：Windows 只有 spawn，
  spawn 会在子进程重新 import 父 `__main__`，三个界面脚本一旦在模块级加启动代码
  就会"点一下弹两个窗口"。这里子进程的 `__main__` 是 worker 本身。
- worker 启动时 `os.dup(1)` 独占真 stdout 当协议通道，再把 fd1 指向 stderr——库里
  的 print/警告不会搅乱字节流。stdin 同理。
- 三处接入：`workcheck._guard(op, *args)`（12 个 lambda 改成 op 形式）、
  `verify._simplify_is_zero`、`solve.solve` 的兜底（`try_run` 区分 TIMEOUT/ERR）。
