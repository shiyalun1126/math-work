# 批改链路：从「判这道题」到「判你写的这一版」

版本 v0.4 · 2026-11-10（v0.1 文字批改；v0.2 §10 拍照批改；v0.3 §11 评测与两个 bug 修复；v0.4 §11.7 真实手写数据入口）

> 前面的 MVP 判的是**题**：把式子认出来，自己解一遍，验自己的步骤。
> 这一层判的是**人**：学生交上来的那一串式子，哪一步开始站不住。

---

## 1. 补的是哪个缺口

`docs/JTBD.md` 把"拍照搜题"拆成三个任务：转录（J1）、判定（J2）、讲通（J3），并声明 J2 是信任枢纽。

但翻回代码看，MVP 的 J2 只做了一半：

| | MVP 现在做的 | 学生实际提交的 |
|---|---|---|
| 输入 | 一道题的式子 | 一整套过程（含题面、中间步、答案） |
| 判定对象 | 系统自己解的步骤 | 学生写的步骤 |
| 结论 | "这题解是 x=2" | "你第 3 步错了" |

差的那一半不是"再多写一个功能"，是**判定对象换了**。这一层补的就是它。

举一个现在必然漏掉的情形：

```
x^2 - 5x + 6 = 0
x^2 - 6 = 5x          ← 移项错了
x^2 - 5x = 6          ← 将错就错
x = 2 或 x = 3        ← 答案是对的
```

MVP 只看最后一行，判"对"；作业帮比对最终答案，也判"对"。
但学生的过程是假的——**答案不是推出来的**。考试按步骤给分，这种写法要扣过程分，学生自己不会知道。

这一层把它判成 `fake`（伪推导），是整个批改链路里最有价值的一类结论。

---

## 2. 判据：局部有效性，不是全局相等

最容易写错的一版是这样：把学生的每一步和标准解法的每一步对齐，对不上就判错。

这个做法会误伤**一题多解**。`x²-5x+6=0` 用配方法和用因式分解，中间步骤完全不同，但都对。
只要判据是"和我算的一样"，学生换一种正确方法就会被判错——这比不批改更糟。

所以判据只有一条：

> **这一步能不能从上一步通过某个合法变换得到。**

相邻两式 `A → B`，按强度依次试：

| 顺序 | 判定 | 判据 | 含义 |
|---|---|---|---|
| 1 | `equiv` | `simplify(d_B - d_A) == 0` | 只是换了写法（整理、展开、因式分解），两边相减仍相等 |
| 2 | `same_solution` | 解集相同 | 合法变形（移项、两边同乘非零数、配方） |
| 3 | `lost` | B 的解集 ⊂ A 的解集 | 只保留了一部分解 → **漏解** |
| 4 | `gain` | A 的解集 ⊂ B 的解集 | 多出了 A 没有的解 → **增根**（两边平方、去分母常见） |
| 5 | `wrong` | 以上都不成立 | 这一步确实不成立 |

第 3、4 条是白捡的：SymPy 的 `solve` 本来就会返回完整解集，做一次子集比较就能抓出漏解和增根。
而这两类错误（开方不带 ±、两边约掉含未知数的因式）是学生最高频的失分点。

---

## 3. 判错是义务，不是权利

一条 ✗ 如果只说"这一步错了"，学生没法核对，只能选择信或不信。这和"讲得很顺但是错的"是同一种失败。

所以代码里有一条硬约束：**判 `wrong` 必须给出反例**，给不出就不判。

反例的构造很直接——找一个满足上一步、却不满足这一步的取值：

```
取 x=9：上一步两边相减为 0，这一步却是 6 ≠ 0
```

`x=9` 是上一步 `2x-6=12` 的解，代进这一步 `2x=12` 得到 6。学生自己一代就知道错在哪。
这条输出不需要任何解释性文字，它本身就是证据。

`workcheck._counterexample()` 的实现顺序：先取上一步的解集当探针，解集为空时退化为 {0, ±1, 1/2, 2, 3}。找不到反例就返回空串，此时该步不判 `wrong`。

## 4. 学生写的人话，是有用的

一条过程长这样：

```
两边同乘2得 2x^2-10x+12=0
所以 (x-2)(x-3)=0
```

`route.py` 会把纯中文行判成 prose 然后丢掉。但在批改场景里，这半句恰好说明**这一步做了什么变换**。

处理方式分两种：

- **能切出式子**（"两边同乘2得 2x²-10x+12=0"）：切出尾巴当式子正常验，前半句记为 `declared`（学生声明的动作）。
- **切不出式子**（"由①得"）：只当说明行，展示，不判对错。

`declared` 和推断出的变换并列显示：

```
「两边同乘」—— 两边同乘 2            ← 对上了
你写的是「移项」，按式子的变化看更像「两边同乘 2」   ← 对不上
```

**对不上不判错。** 推断是启发式的，拿一个猜出来的结论去否定学生，就成了另一种幻觉。
只把两个说法摆在一起，让人自己判断——这和整个项目"不确定就明说"的原则是同一条。

## 5. 结论矩阵

单步判定完之后，还要看两件事：过程通不通、答案对不对。四象限里最危险的是左下：

| 过程 | 答案 | grade | 含义 | 处理 |
|---|---|---|---|---|
| 通 | 对 | `pass` | 逐步可推 | 不记错题本 |
| 通 | 缺 | `partial` | 漏解 | 记错题本，错因「漏解」 |
| 不通 | 对 | `fake` | **伪推导** | 记错题本，优先级最高 |
| 不通 | 错 | `wrong` | 从第 k 步起不成立 | 记错题本，标出第一步 |

另外三档是诚实的降级：

- `unknown`：题面本身求不出标准解（应用题、超范围题型）。此时仍逐步检查了过程内部一致性，但不给"对/错"的总判。
- `gap`：整段没有可验算的式子（"这道题我不会"）。直接说没有可批改的对象。
- `unread`（拍照链路）：有行没认准，且没有一条断言还站得住。给不出结论，把认不出的行摊开让人核对；
  `error_type` 清空，不进错题本。逐行判定里对应 `suspect`（"待核对"，反例已撤回）和
  `unknown`（"跟着待核对"，这一行的"成立"也确认不了）。详见 §10.3。

## 6. 错因归类：按动作，不按题型

错题本里按"一元二次方程"分类没有用——那说明你学到哪一章，不说明你缺什么。
所以 `error_type` 记的是**错的那个动作**：

| 错因 | 怎么检出来 | 典型成因 |
|---|---|---|
| 伪推导 | 有 ✗ 步 + 答案对 | 抄答案，或中途改思路没改过程 |
| 移项/变号错 | `d_B - d_A` 是非零常数 | 移项忘了变号、漏掉一项 |
| 漏乘漏除 | `d_B / d_A` 是非 1 常数 | 两边同乘时只乘了一边 |
| 变形不等价 | 以上都不是 | 计算错误、公式记错 |
| 增根 | B 的解集 ⊃ A 的解集 | 两边平方、去分母没验根 |
| 漏解 | B 的解集 ⊂ A 的解集 | 开方不带 ±、约掉含未知数的因式 |
| 代回不成立 | 解代回上一步残差 ≠ 0 | 算错、抄错 |
| 答案错 | 过程看着通，但答案与标准解集不一致 | 最后一步抄错、整理形式出错 |
| 未写答案 | 过程里读不到 `x=…`，也解不出最后一式 | 只写推导，没落答案 |

前两条是同一套符号运算的副产品：`d = lhs - rhs` 的差如果是常数，说明整条等式被平移了——那正是移项出错的样子；如果是倍数，就是漏乘。

### 6.1 标签的族与选用规则（v0.3 补）

首轮评测暴露了一件事：人工标注写「答案错」、引擎报「代回不成立」，两者指的是
同一个失败模式，但字面不同，严格一致率因此只有 68.2%。**这不是判定错，是缺一份定义。**
按失败模式分族，并写清何时用哪个标签：

| 族 | 标签 | 选用规则 |
|---|---|---|
| 伪推导 | `伪推导` | 有 ✗ 步且答案对，独立一类，优先级最高 |
| 变形 | `移项/变号错` / `漏乘漏除` / `变形不等价` / `增根` | 错在**推导过程**，按 §6 表的符号判据细分 |
| 不全 | `漏解` / `未写答案` | 过程成立但解集不完整；能读出部分解用前者，一个都没有用后者 |
| 答案 | `代回不成立` / `答案错` | 错在**最终答案**：能给出代回残差就用前者（更精确、可验证），只有解集比对不一致时用后者 |

评测里 `eval/run_eval.py` 的 `ERROR_FAMILY` 就是这张表。报两个数字：
**严格一致率**（标签字面相同）和**族级一致率**（归到同一族）。
严格口径低不代表归因差，但它提醒我们标签体系该收敛；是否统一标签属于产品决策，
会改动 `cases.py` 已存数据，留给二期。

## 7. 已知边界

诚实列清楚：

- **拍照的手写体仍在用合成页验证**（`fixtures/work/`，楷体 + 旋转 + 噪点），真实手写还没压过。切行、识别、降级逻辑都按真实链路跑，但识别率数字要等真实数据。
- **一页多道题会被当成一道题批改**。切行只按行带，不判"这行是新题还是上一题的继续"（题号 ①② 前缀目前只当装饰剥掉）。
- **题面必须是可解的式子**。应用题、几何题没有标准解，只能做过程自检（`unknown`）。
- **不判"方法好不好"**。解法绕了远路但每步都对，判 `pass`——批改的是对错，不是优劣。
- **跳步不扣分**。相邻两式同解就放过，不要求中间过程写全。想扣跳步分需要另一套"合法变换白名单"，现在没做。
- **含参讨论不批**。`params.py` 那套分类讨论目前只用于求解，不用于对照学生的分类。
- **题面级不确定性没有传播到标准解**（评测 U05 抓到，v0.3 待修）。题面那行没认准时，
  标准解的来源本身就失效了，但 `_base_sound` 是逐行往回找最近基准的局部规则，
  只撤回直接依赖题面的那一步，后续断言与总判定仍留着。`eval/photo_cases.jsonl` 的 U05
  保留了这条"不通过"的真值，没有为了让撤回召回率好看而改掉。
- **批改评测用的是构造样本**。`eval/work_cases.jsonl` 40 条按已知场景人工设计并标注，
  引擎与评测集出自同一人，存在共同盲区；结论准确率 100% 只说明这批样本内无剩余缺陷，
  **不代表真实作业上的准确率**。见 §11。

## 10. 拍照批改：整页照片 → 切行 → 逐行识别 → 批改

v0.2 新增。链路：

```
整页照片 ──切行──> 单行小图 ──逐行识别──> 每行候选 ──文字投票──> 过程文本 ──> workcheck.grade
                                        │
                                        └── 一致度 / 来源 ──> 不确定性传播（§10.3）
```

### 10.1 切行

`mathagent/lines.py`（从 `tools/split_page.py` 搬进包里，CLI 变薄壳，两边共用同一份算法）：
Otsu 二值化 → 抹掉横线本的长线 → 投影纠偏 → 行带切分 → 过高的行带在谷底再切一刀。
切完带一句自检（"第 3 行明显比别人高，可能两行粘连"）——切错不报错，只会让后面
莫名奇妙地认出怪东西，所以可疑处必须说出来而不是默默给出一堆小图。

**已知缺陷（2026-11-12，M²E 全量评测发现）**：当整张图的行被合并成**一条**带时，
`split_tall` 的参照 `median_h` 就是这条带自己的高度，`h <= 1.6 * median_h` 恒成立，
于是永远不会再切——一张 10 行的紧凑图只能切出 1 行。M²E test 2000 块里有 606 块
（30.3%）是这样，是当前切行最大的单一失败模式。**调参救不了它**（是参照系失效，
不是阈值宽窄），要改的是「一条带怎么估行高」（按投影谷底递归切，或用同一张图其他
带的行高作先验）。整页模式 `_split_page_mode` 走另一条路径，暂不受影响。

试过一版最朴素的修法：在带内找最深的相对谷底（低于带内中位数的 0.35 倍）递归切。
train 上取 12 个单带样本，只有 5 个把行数切对，还把 1 行的图切成 5 行——
**纯谷底法分不清"行间空隙"和"笔画内部空隙"**。所以这条不能靠加阈值解决，得先定
「一条带的行高怎么估」：投影的自相关周期、同图其他带的中位行高、或是按连通域高度
统计。改之前先在 train 上把这条定下来，再动 `split_page`。

### 10.2 逐行投票：按"文字一致"，不按"能不能解析"

这里踩过一个坑：一开始直接复用 `verify.cluster`，结果正确识别出来的两行
（"两边同乘2得 2x²-10x+12=0"、"x=2 或 x=3"）全被判成"没认出来"。
原因是它要求候选解析成**一个** SymPy 表达式才参与等价聚类，
而学生的一行天然混合中文叙述和多个式子，整体解析必失败。

所以 `photocheck._vote` 只做与数学无关的归一（空白、全角、`²` ↔ `^2`），
按"两个来源读出了同一句话"投票；`readable()` 只剥 `\text{...}` 和 `\left/\right`，
**数学结构一个不动**——用 `route.plain()` 会删掉花括号，把 `\frac{1}{2}` 变成 `\frac12`。

还有一条硬规矩：**判错要有旁证**。只有一个来源读出内容的行，可能是模型在编——
对着空白或涂改块，视觉模型经常硬凑出一个像样的公式。实测就撞上过：
一块灰色涂改被单来源"读"成一个分式方程，差点判学生错。
所以环境里有两个识别器时，单来源一律降为 `review`；只有一个识别器时放宽
（否则"要旁证"等于"永远判不了"），但一致度封顶 0.8。

### 10.2.1 公式链路的投票口径（`verify`）

`photocheck._vote` 比的是"是不是同一句话"，`verify` 比的是**语义**。后者有三条
容易写错、写错就很严重的地方：

1. **旁证按赢家算，不按全场算。** qwen 两个版本都说 `x=1`、glm 说 `x=2`，
   全场厂商数是 2，可赢家里只有 qwen 一家。拿反对票的厂商当"独立旁证"，
   等于自己给自己背书。现在的判据是 `win_vendors >= 2`；赢家没有第二个厂商、
   而另一派又给了不同答案时，一律 `review`。
2. **方程组不能求和。** 把 `{x+y=3, x-y=1}` 和 `{x+y=30, x-y=-26}` 各自相加，
   都是 `2x-4`——两个解不同的题被投成一簇，多源投票还把这个当成"一致"。
   `systems_equivalent()` 逐条比：条数相同、每条都能在对方那里找到只差一个
   非零常数倍的那条。这比"同解集"严（`{x+y=3,x-y=1}` 与 `{x=2,y=1}` 过不了），
   严是有意的——判成"没认准"只是多看一眼，判成"一致"是两个错读互相背书。
3. **近似相等不能传递。** 0、6e-10、1.2e-9 两两相邻都在容差内，首尾超出；
   用并查集合并会得到一个"三票一致"的假簇。聚类改成**只跟簇代表比**，
   簇里每个人跟代表都在容差内，"一致"这句话才站得住。

### 10.3 识别错误不能算学生错（整个模块的要害）

一行认错，`workcheck` 会照常给出反例、照常判"这一步不成立"，而且看起来毫不含糊——
因为它是拿认错的那行当真值算的。批改系统冤枉一次，之后所有"你错了"都不作数。

`_apply_uncertainty` 把每行的可靠程度灌进结论里，三条规则：

| 情形 | 处理 |
|---|---|
| 这一行自己没认准，却判了"不成立" | 降为 `suspect`，**反例作废**、原 reason 一起换掉 |
| 这一行自己没认准 / 判定基准跨过了窟窿，却判了"成立" | 降为 `unknown` |
| 真错、真成立的断言一条都不剩 | 总判定改 `unread`，`error_type` 清空 |

**"成立"也要撤回。** 冤枉人和错夸人是同一种装作确定，只是方向相反。
另外：没认准的行在过程文本里留 `?` 占位，**不删**——删掉会让后面的行错位，
把"A 和 C 相邻"当成"A 和 B 相邻"；`?` 没有中文，才会被判成"读不出算式"并明确标出来。
没认准的行超过三分之一，整份不给总判定（相邻两式比较要求上下行连着）。

**题面那一行没认准，整份直接不判。** 上面三条管的是"这一行和上一行"，
但批改里还有一半结论是相对**题面**算的：标准解是从题面解的，"伪推导"（答案对、
过程错）整套判断更是完全靠标准解撑着。题面悬空时这些结论一条都不成立，
尤其"伪推导"那顶帽子扣错了最伤人。所以 `_withdraw_on_bad_problem` 会撤掉
标准解、撤回所有 `wrong/partial`、把总判定改成 `unread`，并在结论里点明是第几行。

`unread` 不进错题本：它不是学生的错，写进错题集会污染"按错因统计"的整张表。

### 10.4 认不出时由人补（手动修正）

切行必须切全，但识别**允许多行认不出**。认不出的行在界面上摊成一段可以改的文本，
每行前面带原行号；改完点「按我改的重新判」——不重新拍照、不重新调用模型，
只把新文本重新过一遍 `workcheck`（纯本地计算，几百毫秒）。

规则只有一条，但要拆成三种情形。区别只在一件事上：**这个式子是系统看清的，还是人给的**。

| 这一行 | 处理 | 为什么 |
|---|---|---|
| 改过 | 标 `ok`／置信度 1.0／来源 `手输`，结论里点名 | 系统没核对原件，不能把用户的判断算成自己的功劳 |
| 没改，但勾了「核对」 | 同样当确定，来源 `核对` | 原文本来就对，只是两个来源没谈拢 |
| 没改也没勾 | 保持原来的把握，窟窿还是窟窿 | 见下 |

第三条是这套机制的要害。`y=2` 被读成 `7y=2` 时，用户只改了别的行、这一行原样留着，
要是当成他写的，接下来判出来的「不成立」全是冤案——一个「允许修改」的入口，
反而成了新的冤枉来源。所以**默认不确认**：想确认，得单独勾一下。

行号只用来对齐，不参与判定（`workcheck._ENUM` 会剥掉）：改完只剩六行时，
系统还得知道哪一行是原来的第 10 行，否则原来那行的「没认准」会张冠李戴。
整行删掉＝这行不存在；漏切的行补一行（前面不写数字）会插在它所在的位置——
判定按文本顺序走，号只是标签。

**题面那一行要跟着改。** 页面上第一行通常就是原题，`workcheck` 会拿它当判定基准，
行号记在 `PhotoCheck.problem_line` 里。用户改的正好是这一行时，题面必须换成改过的
那个式子——沿用旧题面会拿错题判新过程：`x²-5x+7=0` 改成 `x²-5x+6=0`，学生写的
`x=2`、`x=3` 明明全对，却会被判成「解不全，少了两个复根」。改对一次反而更错，
比不许改还糟。题面行被删掉时退回原标题，并在结论里说清；题面是用户填在输入框里的
（`problem_line == 0`）则一律以输入框为准。

### 10.5 界面上的四件东西

1. **逐行小图画廊**：认成什么、多大把握，直接对着原图核对；
2. **识别账本**（每行候选、来源数、别的可能）：结论错了根子多半在这张表里，
   所以必须和结论一起出现，不能藏进"高级设置"；
3. **手动修正框**：见 10.4，认错的行直接改、认对但没把握的行勾一下，不用重拍；
4. **批改结论表 / 正确做法**：与手打文字完全同一个 `workcheck`，没有第二套判据。

### 10.6 实测

三张合成作业照（楷体 + 旋转 1.1° + 噪点 + 模糊，模拟整页照），两个独立 VLM 逐行识别：

| 样例 | 行数 | 结论 | 错因 |
|---|---|---|---|
| `work_ok` | 4 | `pass` | — |
| `work_fake` | 4 | `fake` | 伪推导 |
| `work_miss` | 3 | `partial` | 漏解 |

把中间一行涂改成灰块后：那两行被单来源幻觉成公式 → 全部标"待核对" →
`unread`，整份不判。冷启动约 4 秒 / 页（4 行 × 2 来源并发），
命中磁盘缓存后约 1 秒。

### 10.7 还没做的

- **真实手写数据没压过**：合成页能验证链路，验证不了识别率；答辩前该用真实作业照跑一轮。
- **两个独立模型对着同一块污渍同时编出相同公式**的残余风险仍在（概率低但非零）。
  真正的兜底是"识别账本 + 人工可改"（见 10.4），不是再加第三个模型。
- **一页多道题**会当成一道题批改（切行按行带，不认题号边界）。
- **多行手写的复杂版式**（分式、方程组、大括号）会被行带切碎，目前只吃"一行一步"。
- **拍照链路不接几何题**：几何页签是另一套 `geoagent` 链路，没有合并。

## 11. 批改评测（v0.3）

### 11.1 为什么要另起一套指标

`docs/项目技术文档.md` §6 的 8 个指标（ExpRate、语义等价率、干预率、幻觉率……）
全部围绕「识别 → 求解」链路，**批改能力一个都没覆盖**。而批改恰恰是现在最该拿数字
说话的部分：伪推导召回率、冤枉率、错因归因、拍照撤回，没有一个能从原有指标里推出来。

更关键的是：批改吃的是**文本**，不需要真实手写照片，所以这套评测在 `data/test/` 为空的
情况下也能立刻跑，不等采集。这是 S3 里唯一能马上出数字的一块。

### 11.2 真值怎么来

`eval/work_cases.jsonl` 40 条，六组：正常与一题多解、伪推导、漏解、明显错、无法判定、
版式与叙述。每条按**数学规范人工标注** `grade` / `first_error` / `error_type`，
写的时候不看引擎输出。

三条纪律：

1. **不从实现反推真值**。跑完先列不一致，逐条裁定是「标注口径」还是「引擎 bug」；
2. **引擎 bug 只修引擎，不改真值**（F02、C04）；
3. **口径分歧只改真值并留修订记录**（C03），报告 §8 列出 ID、原值、新值、理由。
   真值文件带 sha256 记在报告抬头，可与历史运行对照。

`eval/photo_cases.jsonl` 9 条用构造的 `LineRead` 模拟「哪一行没认准」，不调 VLM，
标注的是"该撤回哪些断言"和"总判定该不该降成 `unread`"。

### 11.3 指标

| 指标 | 口径 |
|---|---|
| 结论准确率 | `grade` 与真值一致 / 全部 |
| **冤枉率** ↓ | 真值 `pass` 却被判 `wrong` / `fake` / `partial` 的比例 |
| 漏抓率 ↓ | 有错的过程被判 `pass` 的比例 |
| **伪推导召回率** ↑ | 真值 `fake` 里判成 `fake` 的比例 |
| 首错定位准确率 | 只在有错的样本上比 `first_error` 行号 |
| 错因归因准确率 | 严格口径 + 族级口径，都只在标了错因的样本上算 |
| 撤回 P / R / F1 | 该撤回的断言 vs 实际撤回的断言 |
| 无假确定 / 反例作废 / 总判定守门 | 认不准行不残留断言；撤回时清空反例；全撤回降 `unread` |

比例一律附 bootstrap 95% 置信区间（1000 次、固定种子 20261110），与技术文档 §6.3 一致。

### 11.4 首轮就值回票价

首轮 38/40，抓到两个 135 项单元测试全过也没发现的真 bug：

| ID | 现象 | 根因 |
|---|---|---|
| F02 | 「解得 x=2 或 x=3」只认出 `x=3`，全对的过程被冤枉成漏解 | 中文前缀在按「或」切分之后才剥离，第一段带「解得」解析失败 |
| C04 | `x^2=x` 整道题作废 | `_as_assign` 把 `x^2 = x` 反过来当成「x = x²」的赋值 |

顺带修了一处不诚实文案（C03）：答案是系统从最后一行式子解出来的，
原来却写「过程逐行成立，答案也对」，把系统补的东西算到学生头上。

修复后：结论 40/40、冤枉率 0、伪推导召回 8/8、首错定位全中；
错因严格 76.2% / 族级 100%（差异全部来自标签命名，见 §6.1）。
拍照撤回 P 100% / R 92.9%，唯一未通过的是 U05（题面级不确定性未传播，§7）。

### 11.5 这组数字不能怎么用

**100% 不是能力证明。** 样本按已知场景构造，引擎与评测集出自同一人，有共同盲区；
它只说明「这批构造样本内已无剩余缺陷」。真实手写作业的分布、应用题、含参讨论、
复杂版式一律没覆盖。报告里把这个警告放在主指标表正下方，不许被单独摘出来引用。

要往外推，必须有 `data/test/` 的真实手写数据，以及独立标注员（不能是写引擎的人）。
在那之前，这组数字的正确用法是**回归护栏**：`tests/test_eval.py` 断言
「冤枉率必须为 0」「伪推导召回必须为 1」「撤回精确率必须为 1」，谁改坏了立刻红灯。

### 11.6 加样本

往 `eval/work_cases.jsonl` 追加一行即可，字段：
`id / group / problem / work / grade / first_error / error_type / note`。
`first_error` 用 `-1` 表示没有不成立的步骤（答案多写一个根也算 -1）。
然后重跑 `-m eval.run_eval`，报告会自动重算；真值 sha 变化会体现在抬头，
方便区分「引擎变好了」和「换了一批题」。

### 11.7 真实手写数据入口（v0.4）

§11.5 说得很清楚：构造文本上的 100% 不是能力证明。往外推的入口已经建好，
采集规格见 `docs/手写数据采集清单.md`，这里只说它和文本评测的接口差别：

- 真值在 `data/work_shotlist.csv`，20 页、每页一题，**按错法分组**（正确 / 伪推导 /
  明显错 / 漏解 / 无法判定 / 拍摄退化 / 版式压力），不是按题型。每行都带
  `baseline`——文字版引擎的输出。拍完若与 baseline 不同，差异来自识别，不来自判据。
- `eval/run_photo_eval.py --collect` 逐页调 `photocheck.check()`，结果快照落
  `data/photo_results.jsonl`；`eval/run_photo_eval.py` 读快照出
  `reports/eval_photo_real.md`。采集与出表分开，重跑报告不重复花钱。
- 指标沿用 §11.3，另加「撤回正确率」和「与文字基线不同」两项。后者不是错误率，
  用来把"识别读错字"和"判据有问题"分开：报告的不一致表会把系统读出的 `text`
  和清单的 `lines` 并排。
- `--smoke` 是离线假结果，只验证报告管线，写 `reports/_smoke_photo_real.md`，
  **不污染正式报告路径**，抬头也标注了不可引用。

**首轮实测（P0 八页，2026-11-11 上午，旧压缩图）**：

| 指标 | 数值 | 命中 |
|---|---|---|
| 结论准确率 | 62.5% | 5/8 |
| 冤枉率 | **0.0%** | 0/2 |
| 伪推导召回 | **100%** | 1/1（W05，作业帮判 pass） |
| 撤回正确率 | **100%** | 2/2（W16 涂黑行、W17 阴影行） |

首跑只有 25%，两个 bug 修完到 62.5%：
1. `readable()` 里 `\\(?:left|right)\s*` 不带边界，把 `\rightarrow` 削成 `arrow`——
   识别结果里那些莫名的 `arrow` 就是它，两来源从此判成两派。
2. 行首推导符（`⇒` / `\rightarrow` / `arrow`）不参与归一，同一行被读成三种写法后投票作废。
   现在 `readable()` 统一剥行首推导符，句子中间的箭头不动。

剩下 3 页（W01/W04/W12）仍是 unread，原因是**图片被压缩**：
上传件只有 28~90 KB、960×1280、无 EXIF（正常原图 2~4 MB）。
`tools/check_photo_quality.py` 可以拍完就查——判定口径是锐度 <2.5 或墨占比 >0.28 的行算不合格，
不合格行占四成以上整页重拍。**换原图后必须重测，上面这三个数字才有引用价值。**

**重拍后实测（2026-11-11 下午，原图 + 光照拉平）**：

| 指标 | 数值 | 命中 | 与上午相比 |
|---|---|---|---|
| 结论准确率 | **75.0%** [50, 100] | 6/8 | +1 页（W04） |
| 冤枉率 | **0.0%** | 0/2 | 持平；正确过程组 2/2 全对 |
| 伪推导召回 | **100%** | 1/1 | 持平 |
| 撤回正确率 | 50.0% | 1/2 | −1 页（W17，见下） |
| 与文字基线不同 | 25.0% | 2/8 | 上午 62.5%，识别引入的差异大幅减少 |

剩下的两页不是同一类问题：

- **W12 第三行 `x=2` 认不准。** 学生把 2 写成了"∨"形，两个来源分别读成 `x=v` 和
  `-3x=4`。试过 4 倍放大、二值化、加粗、反锐化、拉伸五种预处理，五种都是 `V`/`4`——
  这是字形歧义，不是分辨率问题，只能判"没认准"。改成 unread 是**正确行为**，
  这一页属于"应当撤回而确实撤回了"，只是没有命中真值。
- **W17 真值需要复核。** 真值 `unread` 是按旧压缩图定的（阴影让笔画糊掉，
  应收回结论）。换原图后四行都读得出来，系统判 `fake`——与文字基线一致，
  也与学生的实际写法一致（第二步 `x²-5x+6=0 → x²-6=5x` 确实错了号）。
  这一页现在的问题不是引擎，是**真值过期**：重拍改变了"这张图能不能看清"这个前提。
  在复核之前，撤回正确率按 1/2 记，不按 2/2 记。

这一轮修的四个缺陷，每一个都对应一条实测证据，不是参数调优：

| 缺陷 | 证据 | 改法 |
|---|---|---|
| 切行把上标切在框外 | W04 第一行 `x²-5x+6=0` 两条来源都读成 `x-5x+6=0`；放大裁框后 glm 立刻读出 `x^2` | `lines.widen_boxes()`：向上放宽 0.32 倍行高，用相邻框中缝夹住 |
| 措辞不同被当成数学分歧 | W04 第四行"所以：(x-2)(x-3)=0" vs "所求点：(x-2)(x-3)=0" | 旁证按 `_math_key`（去掉中文后的式子）重新数，不按整行分组数 |
| 说明行被算成窟窿 | W04 第二行"两边同时乘2得"，措辞分歧把整页拖成 unread | 新增 `prose` 档：只有文字、主模型也没读出式子时不参与判定 |
| 平票只能看上一行 | W04 第一行没有上一行，可下面第三行正好是它的 2 倍 | `_tiebreak_by_math()` 支持"往上找不到就往下看"，并允许"两种写法同解"直接判 ok |

另外三处是"字读对了、清洗没跟到底"，都在 `readable()` 里：行首 `⇒` 被读成 `=7`
（等号不可能在行首，`\d+` 后带空格才当影子剥）、行首孤立右括号（大括号跨行的残留）、
行尾悬空等号（`...=` 按 `...=0` 比对）。
`workcheck._LEAD_WORD` 也补了连接词后的冒号——"所以：(x-2)(x-3)=0" 原来会把 `：`
留在行首，整行退化成"读不出算式"。

还有一处是判错门槛：行首多一个数字（`⇒` 被读成 `2`）不判错。
判据不是"看着像"，而是**去掉这个数字后与上一行同解**才撤回；真写错系数时
去掉也接不上，照常判错。W17 第三行因此从"这一步和上一步不同解"降为"待核对"。

### 11.8 评测数字要能被别人复算（v0.5）

只存汇总的报告有个致命问题：数字变了，没人知道是哪几块变了、是代码改了还是换了数据。
验收时被问"请现在从图片重跑一次"时，一份只有百分比的报告什么也回答不了。

**切行评测（`eval/run_line_eval.py`）**现在会落这些：

| 字段 | 内容 | 为什么必须有 |
|---|---|---|
| `records` | 每块 `id / n_true / n_pred / delta / exact / within1 / group / align_group / size / note` | 任意指标都能只靠这堆记录重算，不用再跑一遍切行 |
| `seed` / `n_boot` | bootstrap 重采样种子与次数 | 区间是随机量，不写种子等于没写 |
| `inputs.blocks_sha256` | 标注文件字节的 sha256 | 换了一份数据，数字不可比 |
| `inputs.labels_sha256` | `(id, n_lines, has_align)` 序列的 sha256 | 文件没变但标注内容改了也能发现 |
| `inputs.params_sha256` | 生效参数的 sha256 | 参数变了不算回归 |
| `n_blocks` / `n_loaded` / `inputs.limit` | split 总块数 / 本次载入 / 截断数 | 旧报告把 `--limit 500` 写成了"该 split 共 500 块"，直接误导读者 |

报告 md 里同步给出**偏差直方图**和**偏差最大的 15 块**（按 `|delta|`、同分按 id 稳定排序），
打开报告就知道先目检哪几张。复核链路是：按 ID 去 `data/public/m2e/blocks.jsonl` 找记录 →
对该图单独跑 `split_page` → 看 `size` 判断走了块模式还是整页模式。

**照片评测（`eval/run_photo_eval.py`）**加了两条：

- `--results PATH`：显式指定结果快照，支持 `.jsonl`（每行一页）和 `.json`（本脚本自己
  写出的 `{summary, records}`）。原图涉隐私不入库，但脱敏快照可以；评审要复算时
  应该能对它指定的那份跑，而不是读 `data/` 下"上一次运行顺手留下的"文件。
  报告抬头会写快照路径，并声明**只保证指标可复算，不等于重跑了识别**。
- **没有可用快照时退出码是 2（未执行），不是 0**，也不写报告文件。以前这里
  `return 0`，日志看着像"评测通过"，其实一个字都没测——这类"静默通过"比报错危险。
  切行评测同理：`评测 0 块` 也是退出码 2。

复算示例（不依赖任何引擎）：

```python
recs = json.load(open("reports/eval_lines.json", encoding="utf-8"))["records"]
exact = sum(r["exact"] for r in recs) / len(recs)          # 报告里的 exact 点估计
mae = sum(abs(r["delta"]) for r in recs) / len(recs)        # 报告里的 MAE
```

两份报告数字对不上时的排查顺序：**先比三个指纹**（输入变了就不可比）→ 再比
`records` 里同 ID 块的 `n_pred`（代码变了）→ 最后才怀疑指标算法。

## 12. 超时守卫：到点要真的停下来（v0.5）

**问题不是"等多久"，是"算不完怎么办"。** 原来的写法是三处各自开一条 daemon 线程
（`workcheck._guard`、`verify._simplify_is_zero`、`solve.solve` 的兜底），
到点 `join(timeout)` 返回。但 `join` 只让**调用方**不等了：

- 那段 sympy 还在跑，而且握着 GIL。CPython 里 `simplify` 大部分时间在 C 层，
  主线程要拿 GIL 才能把"超时"这个结论返回给用户，拿不到就还是卡着。
- 线程杀不掉。`PyThreadState_SetAsyncExc` 只在两条字节码之间生效，对 C 层循环无效。
- 于是超时会**堆积**：一页里连着几次，进程里就躺着几条还在算的线程，
  界面越用越慢，直到"超时"这个兜底本身也失效。

评测里量到的样子是「跑 20 次超时，20 个后台任务存活」。

**改法：换进程。** `mathagent/guard.py` 起一个常驻 worker（`mathagent/_worker.py`），
一次跑一件事，二进制长度前缀 + pickle 通信：

```
父 → 子   b"\x01" + uint32 长度 + pickle((op, args))
子 → 父   b"\x01" + … + pickle(结果)          b"\x00" + … + pickle((类型名, 消息))
```

- **超时 = kill。** `kill` 之后管道断开，读线程随即看到 EOF 自己退出——
  它阻塞在系统调用里，不占 GIL，也不烧 CPU。进程表里不留东西。
- **崩溃不重试。** 子进程跑到一半死了（OOM、段错误）算这一次失败，只重启不复算：
  同一道题再跑一遍大概率还是崩，重试只会把卡死时间翻倍。
- **stdout 是协议通道。** 子进程启动时先把 fd 1 复制出来独占，再把 fd 1 指向
  stderr——任何 `print`、警告、进度条都改道，不会把字节流搅乱。stdin 同理。
- **为什么不是 `multiprocessing`。** Windows 只有 spawn，而 spawn 会在子进程里
  重新 import 父进程的 `__main__`；三个界面脚本的 `demo.launch()` 虽然都在
  `if __name__ == "__main__"` 里，但这条路一旦有人在模块级加一行启动代码，
  就会变成"点一下卡死弹两个窗口"。`-m mathagent._worker` 让子进程的 `__main__`
  是 worker 本身，跟界面无关。

**代价。** 首次调用 ~0.7 秒（import sympy），三个界面入口在 `__main__` 里调
`guard.warmup()` 提前拉起，用户感知不到。之后每次运算是一次管道往返：
`ping` 实测 0.21 ms，相对于 `simplify` 本身（小表达式 4 ms 量级）可以忽略；
整份文本批改 5 次 1.26 秒 vs 线程版 0.57 秒，全量测试 79 秒 vs 74 秒（+5%）。
超时一次多付 ~1 秒重启。

**起不来的环境。** 沙箱禁 `exec`、嵌入式解释器之类，spawn 会失败：这时退回线程
（会退化成"只能停止等待"），并往 stderr 打一行说明，功能不至于整个没有。
`MATHAGENT_GUARD=thread` 可以强制走这条路，用来复现旧行为或排障。

**同批修掉的一条。** `equivalent` 压成 `lhs-rhs` 之后判零，`x=1` 与 `1=x`、`2x=2`
差的是一个非零常数倍，判零抓不到——两个模型把同一行读成同一个方程的两种写法，
会被当成"两派各一票"。现在方程之间补一步"只差非零常数倍"（表达式不适用：
`x` 和 `2x` 是两回事）。

**同批修掉的第二条：读错的题面行不能再算"学生的第一步"。** 人在输入框里填了正确题面、
页面上那一行却读错时（`x²-5x+7=0` 对 `x²-5x+6=0`），原来这一行会当成第一步，
后面的答案拿它当基准比，判出「过程有一步不成立，但最终答案是对的」——**伪推导**，
这套系统里最重的罪名，而学生其实全对。

现在：题面是外面给的、页面上又没有一行对得上时，若首行与题面"同未知数 + 字面高度相似
（≥ 0.75）"，就把它认成题面，**基准换成人给的那道题**（`role="problem_misread"`），
并在结论里写明"这一行不参与比对"。判据要"像同一道题的两种写法"，不能放宽：
学生真正的第一步（`2x²-10x+12=0`）跟题面差得远，不会被吞掉。
另外"认题面"这一步用**严格等价**（两边相减化简为零），不走"差一个非零常数倍"——
否则 `2x=6` 与题面 `x=3` 会被当成抄题，那一步就永远不参与判定。
投票那边相反，差倍数就算同一个答案（见 §10.2.1）。

## 13. 时间预算：把"最坏情况"从两小时压到一分钟（v0.6）

**§12 管的是"算不完要停"，这一节管"根本别在那儿等那么久"。** 两件事不一样：
守卫约束的是**单次符号运算**；而一次拍照批改要发一打 HTTP 请求，每个请求
都有自己的超时，乘起来才是用户实际盯着页面的时间。

### 13.1 原来的上界

`HTTP_TIMEOUT = 90` 秒单看很正常，但 `VLMRecognizer._one()` 的循环是
`(THROTTLE_RETRY + 1) 轮 × 候选模型数`，第二路有三个候选模型：

| 环节 | 最坏耗时 |
|---|---|
| 单个请求 | 90 s |
| 单通道一轮（3 个模型全 429） | 270 s |
| 单通道 3 轮 + 退避 4 + 8 s | **822 s** |
| 整页 24 行、并发 2 | **约 2.7 小时** |

这些数字在服务正常时一次也看不到——只有限流或网络变慢时才暴露，而那时候
用户已经盯着转圈的页面，还以为是自己的图有问题。没有一个环节是"错"的，
错的是**没有人在总闸上装表**。

### 13.2 改法：一个 Deadline 从入口传到每个请求

`mathagent/perceive.Deadline` 记的是"这次调用还剩多少秒"，三个动作：

1. `cap(timeout)` 把单个请求的超时压进剩余预算——否则预算只是摆设，
   剩 2 秒时照样发一个 90 秒超时的请求，用户还是等 90 秒。
2. `expired(reserve)` 在发请求**之前**问一句"还剩多少"，不足就别开始。
3. 退避的 `sleep` 之前也算一次：睡 4 秒是为了"下一轮还有机会"，剩余预算
   不够再发一次请求时，这 4 秒纯属白等。

预算用完之后**不抛掉已有结果**：已经拿到的候选照常参与投票，只是不再发新请求。
慢的那一路缺席只影响旁证强度，不该连已经认出来的行一起丢——"因为想多问一句，
反而一句都不答"是比慢更糟的失败。

超时用 `BudgetExhausted`（`RecognitionError` 的子类）单独标出来，因为
"这一行没认准"和"这一页没时间认"要说不同的话。混成一句，学生会以为是自己写得不好。

### 13.3 现在的上界（可以照着报）

预算按行数给，因为耗时基本跟行数成正比：`12 + 5n` 秒（`BUDGET_BASE` /
`BUDGET_PER_LINE`，环境变量 `MATHAGENT_BUDGET` 可覆盖，设 0 表示不限）。

| 场景 | 上界 |
|---|---|
| 单题（`pipeline.run`） | 22 + 8 + 1 ≈ **31 s** |
| 整页 6 行（`read_page`） | 42 + 8 + 1 ≈ **51 s** |
| 整页 24 行（`MAX_LINES`） | 132 + 8 + 1 ≈ **141 s** |

（8 s 是 `SOLVE_TIMEOUT`，1 s 是解析/校验/讲解的余量。）

**"10 秒端到端"目前不成立**，差距在识别——冷启动 P95 已经 14.55 s（见下）。
能如实说的是：有确定上界、超时对用户可见、任务不堆积；不能说"10 秒内返回"。

### 13.4 实测分布

`python tools/timing_report.py` 汇总 `runs/*.json` 里的 timings
（本机历史，不是压测，2026-11-09~11-10 共 124 次）：

| 阶段 | n | P50 | P95 | max |
|---|---|---|---|---|
| perceive | 124 | 0.01 | 11.27 | 21.73 |
| verify | 124 | 0.05 | 0.50 | 0.96 |
| parse | 124 | 0.01 | 0.05 | 0.40 |
| solve | 124 | 0.01 | 0.32 | **79.67** |
| explain | 96 | 1.34 | 1.89 | 2.40 |
| **合计** | 124 | **1.62** | **13.67** | 85.19 |

按识别有没有命中缓存分开看，差别全在 `perceive`：

| 分组 | n | perceive P50 | perceive P95 |
|---|---|---|---|
| 冷（真打网络） | 49 | 2.90 | **14.55** |
| 热（缓存命中） | 75 | 0.00 | — |

合计超过 10 秒的有 13 次（10.5%）。`solve` 那条 79.67 s 是 2026-11-09 的记录，
**早于守卫（§12）上线**；现在的上界由 `SOLVE_TIMEOUT=8` 决定。
报告里连同时间范围一起给，就是为了避免拿旧数字当现状。

结论：慢的不是求解，是识别；而识别的慢主要来自"等一个最终会超时的请求"，
这正是 13.2 要解决的。要让 P95 进 10 秒，需要的是更快的通道或更全的缓存，
不是再调超时。

### 13.5 超时之后用户看到什么

- 逐行：`LineRead.reasons` 里带 `BudgetExhausted: 本页时间用完了（预算 42s，剩余 0.2s）`，
  结论是"待核对"而不是"没写"。
- 整页：`PageSplit.note` 追加一句"整页识别撞上 42s 时间上限，有 2 行没来得及认。
  已认出的行照常可用；这几行请稍后重试或重新拍一张"。
- 落盘：`timings["recognize_timed_out"]` 记行数、`timings["recognize_budget"]` 记预算，
  事后再看那次为什么慢，不用猜。

### 13.6 接口变更

`Recognizer.recognize(image, k=1, deadline=None)` 多了一个关键字。自己写的识别器
（`tools/diag_lines.py`、测试里的假识别器）不跟着改也不会坏：`call_recognize()`
只在 `TypeError` 明确提到 `deadline` 时回退到旧签名，其他 `TypeError` 照抛——
把真正的 bug 吃掉比不兼容更难查。
