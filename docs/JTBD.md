# 手写数学批改 Agent · JTBD 分析

版本 v2.0 · 2026-11-12（v1 为 2026-11-10）

> 一句话：学生拍下那道题，不是为了要一个答案，是为了要一个人告诉他「你这一步到底错没错」。
> 前者市面上有一百个产品在做，后者几乎没人做——因为做后者要敢说"我不确定"。

**v2 相对 v1 改了三处，都是为了让它对得上现在这个产品：**

1. **主场景从"一行"变成"一页"。** v1 写的时候产品主要处理单题/单行；现在的默认入口是整页拍照，逐行判完再给总判定。这改变了任务定义——用户不再只需要"这一行对不对"，还需要"这一页里哪几行算数、哪几行不算数"。
2. **v1 把 2/7 写成"29% 干预率"，并当成设计目标。错了。** 那是 7 个演示样例的观察值，95% 区间约 4%~71%，且真正的干预从未落盘。v2 把它降级为"未度量"（见 §5 的 O2）。
3. **竞争地图变了。** 2026 年的通用大模型拍照讲题，J3 已经很强、J2 依然是弱项，但它的话术比题库产品更像"我帮你看"。这一栏必须重画。

---

## 0. 为什么这个项目需要一份 JTBD，而不是又一份功能清单

功能清单回答「我有什么」：多源识别、语义投票、SymPy 求解、分步验算、几何引擎。

JTBD 回答「用户雇我来干什么」。这个问题答错，功能做得再多也是在解决没人提交的任务。

这个项目恰好卡在一个典型分歧点上。

| | 任务定义 A（题库路线） | 任务定义 B（本项目） |
|---|---|---|
| 用户来的目的 | 拿到这道题的答案 | 确认我写的这个式子对不对、错在哪 |
| 成功的标志 | 命中题库、返回解析 | 结论可信、错处定位、说得清为什么 |
| 失败的标志 | 搜不到 | 说得很顺但是错的 |
| 边缘情况 | 退化成通用 OCR，质量断崖 | 降级为"没认准/没读准"，把判断权交回用户 |
| 句式 | "帮我把这道题做出来" | "帮我看看我这样写行不行" |

作业帮、小猿搜题这批产品选的是 A，整个技术栈——题库、特征匹配、原题解析——都是为 A 建的。

但学生拍下**自己写的那一版**时，提交的往往是 B。题库里没有"他这一次的第三行"，而那一行恰好是他真正想问的。

**本项目的立足点：不是 A 做得不够好，是 B 基本没人做。**

## 1. 先拆任务：这不是一个 job，是三个

### J1 · 转录："把纸上的东西变成能用的"

| | |
|---|---|
| **触发情境** | 我要把纸上/卷子上的式子弄进电脑、发给老师、贴进作业 |
| **成功判据** | 转出来的东西和我纸上写的语义一致，我能直接用 |
| **失败代价** | 中。抄错了可能自己发现，也可能发现不了 |
| **现有谁在做** | 公式 OCR（SimpleTex、Mathpix）、手打、拍照发给同学让他打 |
| **断在哪** | 手写体、连笔、`x` 与 `×`、`1` 与 `l`、漏笔，这几类错误它自己不知道 |

### J2 · 判定："我这个到底对不对，错在第几步"

| | |
|---|---|
| **触发情境** | 我做完了但不确定；或者我卡在中间某一步，后面全凭感觉往下写 |
| **成功判据** | 明确告诉我错在哪一步、为什么错，而且这个判断本身可信 |
| **失败代价** | **高，且不对称**。说"对"而实际错，我会照抄进作业；说"错"而实际对，我会把对的改掉 |
| **现有谁在做** | 老师（要等）、同学（可能也不会）、搜题 App 的解析（讲的是题库那道题，不是我这道） |
| **断在哪** | **全行业都断在这里**。搜题 App 用"给答案"冒充"判对错"——它给你标准答案，让你自己比。可学生提交的任务是"帮我判" |

### J3 · 讲通："为什么可以这么做，下次我怎么想到"

| | |
|---|---|
| **触发情境** | 我看了答案但没懂；或者我想记住这类题的套路 |
| **成功判据** | 我能用自己的话复述一遍思路，下次遇到同类题能上手 |
| **失败代价** | 中。学不到东西，但当场不会出事 |
| **现有谁在做** | 解析、网课、老师、家教 |
| **断在哪** | 解析常是"答案的复述"而不是"思路的来源"；大模型讲得很顺，但可能把错的讲得比对的还顺 |

### 三个 job 的关系

```
         J1 转录              J2 判定              J3 讲通
    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
    │ 纸 → 可计算的 │───►│ 对不对/错在哪 │───►│ 为什么/下次  │
    │    表达式     │    │              │    │   怎么想     │
    └──────────────┘    └──────────────┘    └──────────────┘
         前置条件            信任枢纽            价值兑现
      （做不好后面全废）  （全行业跳过）      （最容易注水）
```

**J1 是前置条件，J2 是信任枢纽，J3 是价值兑现。**

行业把资源压在 J1（识别率）和 J3（解析好看），默认 J2 会自动成立——"答案都给你了，你自己不会比吗"。

但 J2 不是 J1 和 J3 的副产品。它有独立的成功判据，也有最高的失败代价。

**本项目的核心取舍，就是把工程重心从 J1/J3 挪到 J2。** 代码里能看到：`verify.py` 的语义聚类投票、`pipeline.py` 的 `verdict` 三态、`MathSolveResult.ok` 为假时**根本不生成讲评**、逐行批改里"认不准就不判错"。

### 一个容易漏掉的前置任务

整页拍照把 J1 拆成了两段：**先把这一页切成"行"，再把每行转成式子。**

切错时，用户看到的不是"识别不准"，而是"我明明写了五行，它只判了三行"。这不是转录质量问题，是**输入确认**问题（Job Map 第 4 步）。所以本项目把切行单独当一层（`lines.py`），并且切得可疑时要在页面上说出来，而不是默默给出几个小图。

## 2. 核心 Job Statement

用 Christensen 的句式：`When [情境]，I want to [动机]，so I can [预期结果]`。

### 主任务（v2 重写）

> **当我把写满一页的作业摆到镜头前、心里对其中几步没底时，我想让它把这一页逐行判完、明确告诉我哪一步不成立、哪几行它自己没读准；这样我在交出去之前，知道自己在赌什么，也知道哪些结论不该信。**

v1 的主任务是"看一眼这一行"。改成"一页"之后，多了两个硬约束：

- **"逐行判完"**——不能只挑一行判。用户交的是一整页，只判一行等于让他自己找，那正是他不会做的事。
- **"哪几行它自己没读准"**——整页场景下，不确定的不是某一行，而是"有几行根本没进入判定"。不说清这一点，用户会以为"没标错就是对的"。

### 三个子任务的 Statement

**J1 · 转录**

> 当我把纸上的式子拍下来时，我想让它变成语义一致、可以直接用的形式，**并且当它没认准时让我知道是哪几个字符没认准**，这样我不会把一个错的式子当成对的继续往下算。

注意后半句。普通 OCR 的任务陈述里没有"让我知道"——它默认输出即真相。这一句就是 `confidence` 与 `review` 判决存在的理由。

**J2 · 判定**

> 当我不确定自己这一步对不对时，我想得到一个可以被追问理由的判断，**并且当系统自己也没把握时，它把话说在前面而不是替我做决定**，这样我不会因为一个看起来很顺的错误答案而付出代价。

**J3 · 讲通**

> 当结果和我预期不一样时，我想知道是哪一步的思路分岔了，**而且这个解释不能出现我核对不了的说法**，这样我学到的是能复用的方法，而不是一段听着对的文字。

## 3. 三层任务分解

### 3.1 功能性任务（Functional）

状态按当前代码与实测填：✅ 已成立 / 🟡 有限定域或部分成立 / ⬜ 未做

| # | 任务 | 现状 | 依据 |
|---|---|---|---|
| F1 | 把纸上一页切成"一行一步" | ✅ | 八页实拍 8/8 行数一致；但紧凑小图（短边 <300px）会整页并成一行的失效模式仍在（见 §5 的 O7） |
| F2 | 把一行式子变成可计算的表达式 | 🟡 | 双通道 + 语义投票；手写连笔仍会落到"没认准" |
| F3 | 判断这个式子有没有解、解是什么 | ✅ | SymPy 精确求解，含参分支、增根剔除 |
| F4 | **判断我写的这一版对不对，错在哪一步** | 🟡 | 逐行 `check` 复算 + 反例；限定在声明范围内 |
| F5 | 解释每一步的依据 | 🟡 | 模板讲解绑定已验算步骤；开放题仍靠模型 |
| F6 | 认不准时，让我用最少的动作确认 | ✅ | 点候选即重算；整页里可勾选"核对后没错"的行 |
| F7 | 改一行不用重拍 | ✅ | 手改后重判，题面行被改时判定跟着改（这个细节不做，就会出现"题改了、结论还按旧题算"） |
| F8 | 告诉我这题它到底会不会，别硬撑 | ✅ | `out_of_scope(reason)`；单题连续三次无法判定就停下问人 |

### 3.2 情感性任务（Emotional）

| # | 任务 | 为什么重要 | 现状 |
|---|---|---|---|
| E1 | **不想被一个假装确定的答案骗** | 全部设计的出发点。错得很流畅的解析，比"我不会"有害十倍 | ✅ `verdict` 三态；`ok=False` 不生成讲评；讲评回扫剔除无法验证的等式；题面读不准时整份降 `unread` |
| E2 | 不想显得自己很笨 | 问 AI 比问老师心理成本低，前提是 AI 不反问一堆 | 🟡 追问只在高歧义时触发；但触发率没有度量（O2） |
| E3 | 想知道"我离对还差多远" | 只说"错了"会挫败；"只差一个符号"能继续 | ✅ 候选并列、错因分类（到"因式分解错"这一级） |
| E4 | 想让过程是快的 | 卡住时最烦等 | 🟡 有上界（6 行 ≈51s，24 行 ≈141s），但 P95 13.67s，**"10 秒内"不成立** |
| E5 | **不想等一个不知道要等多久的东西** | 比"慢"更难受的是"不知道还要多久" | 🟡 有硬上界、超时结论可见；界面没有进度提示 |

**E1 是这个项目的灵魂，也是最容易被误读成"技术不成熟"的一条。**

真正的指标不是"有多少次要求确认"，而是**"判成对/错的那些里，有多少本该确认却没确认"**。前者是代价，后者是事故。本项目目前只有前者的机制，没有后者的度量——这是 v2 明确留下的缺口。

### 3.3 社会性任务（Social）

| # | 任务 | 场景 | 对本项目的含义 |
|---|---|---|---|
| S1 | 在老师面前，这个答案能代表我自己 | 交作业、课堂提问 | 必须能说清依据，否则学生复述不出来，反而露馅 |
| S2 | 在家长面前证明"我在学，不是在抄" | 家庭监督 | 分步过程 > 最终答案。只给答案的产品在这条上是负分 |
| S3 | 在同学之间不被看低 | 对答案 | 结论要敢下判断，模棱两可会被嘲笑"问了等于没问" |

S3 和 E1 构成一对张力：**要敢判断，但不确定时不能装。**

本项目的解法不是二选一，而是把"不确定"本身做成有信息量的输出——不是"我不知道"，而是"这两处我拿不准，其余部分已经验算通过"。

## 4. Job Map：用户实际走的八步，和每一步断在哪

| # | 步骤 | 用户实际在做什么 | 现有方案的断点 | 本项目落点 |
|---|---|---|---|---|
| 1 | **定义** | 意识到"这步我不会 / 我可能写错了" | — | 不做（不解决动机问题） |
| 2 | **定位** | 从一沓卷子里找出那道题、那一行 | 整页丢进去，产品只管识别不管定位 | ✅ 整页自动切行，行数可疑时提示 |
| 3 | **准备** | 拍照、调光、摆正 | 手抖、阴影、透视，识别率断崖 | 🟡 自动摆正 → 抹长线 → 裁到墨迹 → 放大 |
| 4 | **确认** | **确认拍进去的是我想问的那一页/那一行** | **几乎全行业缺失**，默认"你传的就是你要的" | ✅ 逐行表 + 置信度 + 候选并列；题面那行读不准时整份降 `unread` 而不是硬判 |
| 5 | **执行** | 得到判定 / 答案 | 题库外退化、答非所问 | ✅ SymPy 求解 + 逐条复算 |
| 6 | **监控** | 判断这个结果可不可信 | 无信号，用户只能靠"看起来顺不顺" | ✅ 总判定 + 理由 + 每步 verdict + "哪几行没算进结论" |
| 7 | **修正** | 改错、重问、换个写法再试 | 改一个字符要重新传图、重新识别、重新等 | ✅ 手改重判，不重拍；题面行改了判定跟着改 |
| 8 | **收尾** | 抄进作业、记住方法、跟人解释 | 解析与步骤脱节 | 🟡 讲评绑定已验算步骤、禁写公式；"记住方法"没有沉淀（错题本未成闭环） |

### 这张表说明了什么

```
现有产品重心：   ████░░░░░░░░░░░░░░░░  ← 全压在 5（执行）
用户真正的痛点： ░░░░░░████████████░░  ← 集中在 4 / 6 / 7
本项目的重心：   ░░░░░░████████████░░  ← 主动对齐用户
```

第 5 步最容易做、最容易演示、也最拥挤。第 4、6、7 步才是用户反复卡住的地方，共同点是：**都要求系统对自己的状态有感知**。

这就是为什么要花力气在验算上：不是为了让答案更准，是为了让系统能回答"我这个答案有多可信"。

几何链路那条规矩最能体现：**任何规则或作图给出的结论，先在解出的坐标上量一遍，对不上整条丢弃。** 它不提高识别率，也不提高解题能力，唯一用途是让"这个结论成立"这句话有据。

## 5. 期望结果（Desired Outcomes）

格式：`[方向] + [度量] + [对象] + [情境限定]`。每条都不含解决方案。

### J2 · 判定（信任枢纽，优先级最高）

| # | 期望结果 | 覆盖 | 现状 / 缺口 |
|---|---|---|---|
| O1 | 最小化「给出确定结论但结论错误」的概率 | 🟡 | 有逐条复算与超范围拒答；限定域内的正确率靠 `eval/` 用例集，样本仍小 |
| O2 | 最小化「系统不确定却没有表达出来」的概率 | ⬜ | **没有度量。** `手输`/`核对` 两个来源在代码里分了，但整页批改不落盘，算不出干预率 |
| O3 | 最大化「标为需确认的样本中，确实存在问题」的比例 | ⬜ | 需人工复核标注，未做 |
| O4 | 最小化「从看到结果到判断可不可信」所需时间 | ⬜ | 只有"理由条数 ≤ 3"这类设计约束，没有实测阅读时长 |
| O5 | 最小化「同一份输入两次运行结论不同」的概率 | 🟡 | 缓存让重复输入必然一致，但这掩盖了模型本身的不稳定；`equivalent_strict` 与宽版两套口径就是为此 |
| O6 | 最小化「结论正确但用户不信」的概率 | ⬜ | 只能用日志推测，不能证明。**这条要写进报告的"未验证假设"** |

### J1 · 转录

| # | 期望结果 | 覆盖 | 现状 / 缺口 |
|---|---|---|---|
| O7 | 最大化「输出与纸上语义等价」的比例 | 🟡 | 整页八页 8/8 行数一致（样本极小）；外部 M²E 2000 块 exact 21.9%，**且不可外推**（见下） |
| O8 | 最小化「认错了但系统以为认对了」的比例 | 🟡 | 无法解析的候选显式标注；单来源一律降"待核对" |
| O9 | 最小化「修正一个字符所需的用户动作数」 | ✅ | 点选 1 次；整页里改一行不用重拍 |
| O10 | 最小化「排版差异被误判为错误」的概率 | ✅ | 判据是 `simplify(a-b)==0`，不是字符串相等；认题面另用严格版避免把 `2x=6` 当抄题 |

**O7 必须配一句限制，这是 v2 新增的诚实条款。**

`reports/eval_lines.md` 里的 21.9% 是 M²E 紧凑公式块（短边中位 155px）的成绩，不是整页作业照的成绩。两种分布不同：整页照走 `page_mode`，不用 `split_tall`；小图走另一条路径，且存在"整页并成一行、再也不切"的失效（2000 块里 606 块）。**引用这个数字时必须同时说"它衡量的是泛化差距，不是产品准确率"。**

### J3 · 讲通

| # | 期望结果 | 覆盖 | 现状 / 缺口 |
|---|---|---|---|
| O11 | 最小化「讲解中出现用户无法核对的说法」的概率 | ✅ | 讲评禁写公式；回扫出现无法溯源的等式整段作废 |
| O12 | 最小化「讲解与已验算步骤矛盾」的概率 | ✅ | 讲评只绑已验算步骤 |
| O13 | 最大化「用户能用自己的话复述思路」的比例 | ⬜ | 需用户调研，无法从日志得到 |
| O14 | 最小化「答案正确但过程被讲错」的概率 | ✅ | `ok=False` 时不生成讲评 |

**O14 对应一条反直觉的决策：算错的时候，宁可不讲。**

`pipeline.py` 里 `sr.ok=False` 直接跳过讲评——**算错的时候讲得越顺，害处越大**。多数产品把讲解当兜底体验：答不出就多讲两句。但 J3 的失败代价是"学错方法"，而错误答案配流畅讲解，恰好是最容易让人学错的形式。

### 新增两类结果：等待与暴露面

| # | 期望结果 | 覆盖 | 现状 |
|---|---|---|---|
| O15 | 最小化「用户等待时间的不确定性」 | 🟡 | 有硬上界（按行数给预算，撞上就退且保留已有结果）；P95 13.67s、>10s 占 10.5%，"10 秒"不成立 |
| O16 | 最小化「派生资产暴露身份」的概率 | ✅ | 原图不进仓库不够——切行图、识别文本、错题本都是同一份作业的另一种形态；已逐项登记来源与授权，CI 拦截 |

O15 的来源是一次自查：`HTTP_TIMEOUT=90` 单看正常，但重试轮数乘上去，整页 24 行的最坏值是**约 2.7 小时**。服务正常时一次也看不到，只在限流时暴露——而那时候用户已经在盯着转圈页面。

## 6. 竞争地图：用户此刻还能雇谁

竞争者不是同类产品，是用户此刻实际会用的所有替代方案，包括"什么都不做"。

| 替代方案 | J1 转录 | J2 判定 | J3 讲通 | 用户为什么还是用它 |
|---|---|---|---|---|
| 作业帮 / 小猿搜题 | 强 | **弱** | 中 | 快、免费、原题有解析 |
| 通用大模型（拍照问，2026） | 强 | **弱** | **很强** | 什么都能问，讲得比解析好懂，还会顺着你说 |
| 公式 OCR（SimpleTex / Mathpix） | **强** | 无 | 无 | 转 LaTeX 准，但不管对错 |
| 问老师 | 无 | **最强** | **最强** | 可信度天花板，但要等到明天 |
| 问同学 | 弱 | 弱 | 弱 | 零心理成本，随时能问 |
| 自己硬啃 | 无 | 无 | 无 | 不用开口，但要耗时间 |
| **抄一份交上去** | 无 | 无 | 无 | **成本最低** |
| **放弃这题** | 无 | 无 | 无 | 零成本 |

### 三个真正的对手

**对手一：抄一份交上去。**

当"搞懂"的成本高于"被抓的概率 × 被抓的代价"时，最理性的选择是抄。任何解题产品在这个对手面前都很弱，因为抄不需要理解。**唯一能赢的角度是降低"搞懂"的成本**——不是给更详细的解析，是让"确认我这一步对不对"这个动作本身变得极便宜。

这正是第 7 步要优化的东西：点一下候选就重算，而不是重传一遍图。

**对手二：问同学。**

零心理成本。E2 说"不想显得自己很笨"——问 AI 有机会，是因为它不知道你是谁。但一旦 AI 开始反问"你说的 x 是字母还是乘号"，这个优势就被削掉一半。所以追问必须克制：**只在真的分岔时问，问的时候给选项而不是让用户描述。**

**对手三：通用大模型（v2 新增）。**

它比题库产品危险，因为它的话术更像"我帮你看"。但它的失败方式正好相反：**它几乎不会说"我没看清"。** 手写潦草时它会顺着上下文补一个合理的式子，然后基于那个式子讲得很顺。用户拿到的是一段流畅的、针对另一个式子的分析。

这恰好是本项目的差异点，也解释了为什么"不敷衍"要写进主任务——不是道德姿态，是对手的结构性缺陷。

### 本项目的竞争位置

```
              可信度 高
                  ▲
        问老师    │        ★ 本项目（限定域内）
                  │
        公式OCR   │   通用大模型（讲得顺，但会替你补式子）
                  │
    ──────────────┼──────────────► 覆盖广度
                  │
        问同学    │   作业帮/小猿
                  │
              可信度 低
```

本项目用**覆盖广度**换**可信度**，在窄域里把可信度做到接近"问老师"——代价是超出范围就明确拒答。

这不是能力不足的妥协，是任务定义的必然结果：**J2 这个任务没法用"大概对"来完成。**

## 7. 从 JTBD 反推设计：每个决策服务哪条任务

这张表是本文档最实用的部分。它回答"如果砍掉某个设计，会伤到哪条 job"。

| 设计决策 | 服务任务 | 砍掉的后果 |
|---|---|---|
| 多源识别而非单模型 | F2 / O7 | 两源架构不同，错误模式才不相关；单源时投票没有意义 |
| 语义等价投票而非字符串相等 | O10 | 排版差异被误判为错误，用户觉得"这都认不出" |
| 低置信降级 `review` 而不是硬给答案 | E1 / O2 | 系统开始骗人；骗人的系统一旦被识破就彻底失去价值 |
| 识别失败返回 `ok=False` 而非抛异常 | 可排查性 | "识别错"和"解析器崩"混在一起，永远查不清是谁的问题 |
| 每条步骤带 `check`，事后逐条复算 | F4 / O1 | 步骤从"可验算的推导"退化成"文案" |
| 增根剔除（代回分母检验） | F3 | 给出数学上无效的解，且用户不易察觉 |
| `ok=False` 时不生成讲评 | O14 | 错误答案配流畅讲解，是最容易让人学错的形式 |
| 讲评禁写公式 + 输出回扫 | O11 / O12 | 大模型会在讲解里塞自己编的等式 |
| 几何结论先在坐标上量一遍 | 第 6 步 / O1 | 规则推出的结论无据，等于凭空断言 |
| 超范围直接 `out_of_scope(reason)` | F8 / S1 | 硬撑的答案学生复述不出来，在老师面前露馅 |
| 点选候选即重算，不重跑识别 | O9 / 第 7 步 | 改一个字符要等一整套流程，用户会放弃修正直接抄 |
| **题面那行读不准时整份降 `unread`**（v2） | E1 / O1 | 题读错了，后面每一行都"有据可查地"判错——这是最坏的一种错 |
| **认题面用严格等价、投票用宽等价**（v2） | O10 | 宽等价会把 `2x=6` 认成 `x=3` 的抄题，然后把抄题判成"没写答案" |
| **识别总预算 + 撞上就退、不丢已有结果**（v2） | E4 / O15 | 最坏 2.7 小时；且"因为想多问一句，反而一句都不答" |
| **符号运算超时用子进程真杀**（v2） | E4 / O15 | 线程 join 只让调用方不等，sympy 还在跑且握着 GIL |
| 图片按 SHA256 缓存 | E4 | 调试期反复计费，迭代速度下降 |

**一句话读这张表：** 除了前两条是识别质量，其余全部服务于"让系统对自己的状态诚实"。这不是技术偏好，是项目选定的任务要求。

## 8. 这个项目自己也要完成一个 job

### 8.1 作者的 job

> 当我要用一个结课项目证明自己真的做过工程判断时，我想让评审在十分钟内看到"这个人知道自己在解决哪个问题、边界在哪、怎么验证"；这样我拿到的评价不止是"跑通了"，而是"想清楚了"。

| 要满足 | 对应产物 | 为什么不能省 |
|---|---|---|
| 让人相信边界是主动划的 | 范围表 + 「明确不做」清单 | 没有边界声明的项目，看起来像没做完 |
| 让人相信指标不是挑好看的报 | 同时报 ExpRate 与语义等价率并解释差值；外部数字注明不可外推 | 只报一个指标，评审会怀疑另一个很难看 |
| 让人相信失败案例是设计的一部分 | 把"要求确认"写成设计目标，但**如实说它没有被度量** | 把缺陷讲成设计最容易被识破；主动说出缺口反而可信 |
| 让人能自己验证 | `pytest` 377 项、`demo.py` 7 例、无需密钥可跑 | 评审不会装环境，一条命令跑起来就是可信度 |
| 让人能复核数字 | 评测 JSON 带逐条 records + 输入指纹，指标可只靠它重算 | 只给汇总数字，等于要求评审信任作者 |

### 8.2 这份 JTBD 本身的 job

> 当评审读技术文档觉得"功能挺多但不知道为什么要这么做"时，我想看到一套把功能和任务对上号的推理；这样我能判断这些功能是长出来的，还是堆上去的。

所以第 7 节是核心，其余是它的前提。

### 8.3 一个诚实的位置说明

本项目在真实市场上并不构成对作业帮的替代——覆盖广度差太远，且依赖单机部署。

它的价值是**证明"限定域可信"这条路线可行且可量化**：在一万道题上做到 60% 覆盖率 + 95% 可信度，与在无穷题上做到 40% 覆盖率 + 60% 可信度，是两种产品哲学。

### 8.4 明确不服务的 job（v2 新增）

有边界才叫定位。以下这些是别的产品该做的事，本项目不做，也不该用它们来评价：

| 不做的 job | 为什么不做 |
|---|---|
| 老师批量批改全班 | 需要题库对齐、学号识别、成绩表导出，是另一个产品 |
| 题库检索 / 原题解析 | 那是任务定义 A，本项目的取舍就是放弃它 |
| 竞赛/超纲难题 | J2 的前提是"能验算"；算不动的题只能诚实拒答 |
| 代替教学 | J3 能讲清一步，但讲不清一个单元 |

## 9. 从这份 JTBD 反推：现在最该补什么

JTBD 的用处不是描述，是排序。按"服务哪条 job × 现在缺多少"排，当前三件事的优先级是这样：

**第一，O2 没有度量，这是最刺眼的一条。**

`手输` 和 `核对` 在代码里是两个来源，说明"用户改过"和"用户确认过"被区分开了——但整页批改不落盘，所以算不出干预率。"系统不确定时有没有说出来"是主任务的第二半句，现在只有机制，没有证据。这件事不涉及算法，只需要把 `PhotoCheck` 的判定与来源写进 `runs/`。

**第二，O6（结论对但用户不信）只能用用户验证，不能用日志。**

最小的做法是拿八页实拍做一次"能不能复述"的小样本：让使用者看完结论，用自己的话说"这页错在哪"。说得出，O6 成立；说不出，说明理由摆得不够近。这件事的结论会直接影响界面，而不是算法。

**第三，单带切分对产品几乎无用，对指标有用。**

606/2000 块真值 ≥3 行只切出 1 行，这条缺陷很显眼，但触发条件是"短边 <400px 的多行图"——手机拍的整页照短边 800~1440px，走另一条路径，八页实拍 8/8。修它能让 M²E 的 exact 从 21.9% 爬到 40% 出头，**对真实使用几乎没有影响**。

所以它的优先级取决于目的：要让外部数字站得住，它是第一；要让用户少等、少被误导，它排在 O15 后面。

**一个反向清单**：以下这些"看起来该做"的事，从 JTBD 看并不急——提高识别率的上限（J2 的瓶颈不在识别率，在"不确定时说不说"）、增加题型覆盖（广度是任务 A 的评价标准）、把界面做得更漂亮（E4 的问题是不确定感，不是美观）。

## 10. 如果只能记住三件事

**第一，行业偷换了任务。**
用户提交的是"帮我判对错"，产品交付的是"给你标准答案，你自己比"。这两件事在少数情况下重合，在大多数情况下不重合——尤其是学生自己写错、或者题库里没有的时候，而这两类恰好是他最需要帮助的时候。

**第二，答案的可信度是产品，不是指标。**
"要求确认"看起来是缺陷，实际是产品在履行"不确定就说"的承诺。真正要压的不是这个数字，是"判成对/错的那些里，有多少本该问却没问"——而这个数现在还没有。

**第三，本项目的全部工程重心在 Job Map 的第 4、6、7 步。**
确认输入、监控可信度、低成本修正。三步的共同前提是：系统要对自己的状态有感知。所以验算不是锦上添花，它是这个产品的本体。
