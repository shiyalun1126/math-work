# 手写数学识别与求解智能体 · JTBD 分析

版本 v1.0 · 2026-11-10 · 结课项目

> 一句话：学生拍下那道题，不是为了要一个答案，是为了要一个人告诉他「你这一步到底错没错」。
> 前者市面上有一百个产品在做，后者几乎没人做——因为做后者要敢说"我不确定"。

---

## 0. 为什么这个项目需要一份 JTBD，而不是又一份功能清单

功能清单回答的是「我有什么」：多源识别、语义投票、SymPy 求解、分步验算、几何引擎。读完它的人只知道系统能做什么。

JTBD 回答的是「用户雇我来干什么」。这个问题一旦答错，功能做得再多也是在解决一个没人提交的任务。

这个项目恰好卡在一个典型的分歧点上。

**同一个动作，两种任务定义：**

| | 任务定义 A（题库路线） | 任务定义 B（本项目） |
|---|---|---|
| 用户来的目的 | 拿到这道题的答案 | 确认我写的这个式子对不对、错在哪 |
| 成功的标志 | 命中题库、返回解析 | 结论可信、错处定位、说得清为什么 |
| 失败的标志 | 搜不到 | 说得很顺但是错的 |
| 边缘情况怎么处理 | 退化成通用 OCR，质量断崖 | 降级为 review，把判断权交回用户 |
| 句式 | "帮我把这道题做出来" | "帮我看看我这样写行不行" |

作业帮、小猿搜题这一批产品选的是 A。它们的整个技术栈——题库、特征匹配、原题解析——都是为 A 建的。

但学生拍下**自己写的那一版**时，提交的往往是 B。

这就是本项目的立足点：**不是 A 做得不够好，是 B 基本没人做。**

一份 JTBD 能把这件事说清楚，也能反过来检验每个模块是否服务于同一个任务。这是本文档的第一个用途。

---

## 1. 先拆任务：这不是一个 job，是三个

把"拍照搜题"当成一个整体任务，是产品分析里最常见的错误。用户在那个瞬间其实在提交三个互相独立、可分别雇佣的任务。

### J1 · 转录："把纸上的东西变成能用的"

| | |
|---|---|
| **触发情境** | 我需要把纸上/卷子上的式子弄进电脑、发给老师、贴进作业、写进笔记 |
| **成功判据** | 转出来的东西和我纸上写的语义一致，我能直接用 |
| **失败代价** | 中。抄错了自己可能发现，也可能发现不了 |
| **现有谁在做** | 公式 OCR（SimpleTex、Mathpix）、手打、拍照发给同学让他打 |
| **断在哪** | 手写体、连笔、x 与 × 、1 与 l、漏笔，这几类错误它自己不知道 |

### J2 · 判定："我这个到底对不对，错在第几步"

| | |
|---|---|
| **触发情境** | 我做完了但不确定；或者我卡在中间某一步，后面全凭感觉往下写 |
| **成功判据** | 明确告诉我错在哪一步、为什么错，而且这个判断本身可信 |
| **失败代价** | **高，且不对称**。它说"对"而实际错，我会照抄进作业，被老师当场抓住；它说"错"而实际对，我会把对的改掉。两种都是净损失，前者更疼 |
| **现有谁在做** | 老师（要等）、同学（可能也不会）、搜题 App 的解析（讲的是题库里那道题，不是我这道） |
| **断在哪** | **整个行业都断在这里**。搜题 App 用"给答案"冒充"判对错"——它给你标准答案，让你自己比对。可学生提交的任务是"帮我判"，不是"给我参考答案我自己比" |

### J3 · 讲通："为什么可以这么做，下次我怎么想到"

| | |
|---|---|
| **触发情境** | 我看了答案但没懂；或者我想记住这类题的套路 |
| **成功判据** | 我能用自己的话复述一遍思路，下次遇到同类题能自己上手 |
| **失败代价** | 中。学不到东西，但当场不会出事 |
| **现有谁在做** | 解析、网课、老师、家教 |
| **断在哪** | 解析常常是"答案的复述"而不是"思路的来源"；大模型讲得很顺，但可能把错的讲得比对的还顺 |

### 三个 job 的关系

```
         J1 转录              J2 判定              J3 讲通
    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
    │ 纸 → 可计算的 │───►│ 对不对/错在哪 │───►│ 为什么/下次  │
    │    表达式     │    │              │    │   怎么想     │
    └──────────────┘    └──────────────┘    └──────────────┘
         前置条件            信任枢纽            价值兑现
      （做不好后面全废）  （全行业跳过）      （最容易注水）
```

**J1 是前置条件，J2 是信任枢纽，J3 是价值兑现。**

市面上绝大多数产品把资源全压在 J1（识别率）和 J3（解析好看），默认 J2 会自动成立——"我答案都给你了，你自己不会比吗"。

但 J2 不是 J1 和 J3 的副产品。它是一个独立的、有独立成功判据的、失败代价最高的任务。

**本项目做的核心取舍，就是把工程重心从 J1/J3 挪到 J2。**

这件事在代码里能看到：`verify.py` 的语义聚类投票、`pipeline.py` 的 `verdict` 三态、`MathSolveResult.ok` 为假时**根本不生成讲评**、几何引擎里每条作图关系都要先在坐标上量一遍。这些都是 J2 的工程，不是 J1 或 J3 的。

## 2. 核心 Job Statement

用 Christensen 的句式：`When [情境]，I want to [动机]，so I can [预期结果]`。

### 主任务

> **当我对着自己写完（或写了一半）的一版式子心里没底时，我想让一个不会敷衍我的东西看一眼，明确告诉我这一步成不成立、依据是什么；这样我才能在把答案交出去之前，知道自己在赌什么。**

三个子句，每一句都是一个硬约束：

- **"不会敷衍我"**——它不确定时不能编。这是情感任务，也是 J2 的技术定义。
- **"明确告诉我"**——不是给参考答案让我自己比，是给判断。
- **"知道自己在赌什么"**——即使答案是"我不确定"，只要它说清了不确定在哪，这个任务也算完成了一半。

### 三个子任务的 Statement

**J1 · 转录**

> 当我把纸上的式子拍下来时，我想让它变成语义一致、可以直接用的形式，**并且当它没认准时让我知道是哪几个字符没认准**，这样我不会把一个错的式子当成对的继续往下算。

注意后半句。普通 OCR 的任务陈述里没有"让我知道"这半句——它默认输出即真相。这一句就是本项目 `RecognitionResult.confidence` 与 `review` 判决存在的理由。

**J2 · 判定**

> 当我不确定自己这一步对不对时，我想得到一个可以被追问理由的判断，**并且当系统自己也没把握时，它把话说在前面而不是替我做决定**，这样我不会因为一个看起来很顺的错误答案而付出代价。

**J3 · 讲通**

> 当结果和我预期不一样时，我想知道是哪一步的思路分岔了，**而且这个解释不能出现我核对不了的说法**，这样我学到的是能复用的方法而不是一段听着对的文字。

## 3. 三层任务分解

同一件事，用户在三个层面上同时有任务。只满足功能性任务的产品，用户会用，但不会信任。

### 3.1 功能性任务（Functional）

| # | 任务 | 现状 | 本项目对应 |
|---|---|---|---|
| F1 | 把纸上那一行式子变成可计算的表达式 | 🟡 | M2 多源识别 + M3 归一化解析 |
| F2 | 判断这个式子有没有解、解是什么 | ✅ | M5 SymPy 精确求解 |
| F3 | **判断我写的这一版对不对，错在哪一步** | 🟡 | 分步 `check` 逐条复算 + `dropped` 剔除 |
| F4 | 解释每一步的依据 | ✅ | 模板讲解 + 步骤绑定 |
| F5 | 遇到认不准的字符时，让我用最少的动作确认 | ✅ | 点选候选即重算，不需重新识别 |
| F6 | 告诉我这题它到底会不会，别硬撑 | ✅ | `out_of_scope(reason)` 边界声明 |

### 3.2 情感性任务（Emotional）

| # | 任务 | 为什么重要 | 本项目对应 |
|---|---|---|---|
| E1 | **不想被一个假装确定的答案骗** | 这是本项目全部设计的出发点。一个错得很流畅的解析，比"我不会"有害十倍 | `verdict=review` 三态；`ok=False` 时不生成讲评；讲评回扫剔除无法验证的等式 |
| E2 | 不想显得自己很笨 | 问 AI 比问老师心理成本低，前提是 AI 不反问一堆问题 | 追问只在高歧义时触发（7 例中 2 例，29%），且给候选点选而非让用户重述 |
| E3 | 想知道"我离对还差多远" | 只说"错了"会挫败；指出"只差一个符号"能继续 | 候选区并列展示、标出无法解析的那条 |
| E4 | 想让过程是快的 | 卡住的时候最烦等 | 端到端延迟 P50 纳入指标；缓存按图片 SHA256，改评测逻辑不重复花钱 |

**E1 是这个项目的灵魂，也是最容易被误读成"技术不成熟"的一条。**

7 个演示样例里 2 例触发人工确认，占比 29%。从纯识别率角度看这是个难看的数据。但从 JTBD 角度看，这 29% 是产品在履行 E1：**该问的时候必须问**。真正的问题不是"为什么有 29% 要问"，而是"剩下 71% 里有多少本该问却没问"——这才是要压的指标。

### 3.3 社会性任务（Social）

| # | 任务 | 场景 | 对本项目的含义 |
|---|---|---|---|
| S1 | 在老师面前，这个答案能代表我自己 | 交作业、课堂提问 | 系统必须能说清依据，否则学生复述不出来，反而露馅 |
| S2 | 在家长面前证明"我在学，不是在抄" | 家庭监督场景 | 分步过程 > 最终答案。只给答案的产品在这个 job 上是负分 |
| S3 | 在同学之间不被看低 | 对答案 | 结论要敢下判断，模棱两可会被嘲笑"问了等于没问" |

S3 和 E1 在这里构成一对张力：**要敢判断，但不确定时不能装**。

本项目的解法不是二选一，而是把"不确定"本身做成一种有信息量的输出——不是"我不知道"，而是"这两处我拿不准，其余部分已经验算通过"。这比沉默和硬猜都更接近完成 S3。

## 4. Job Map：用户实际走的八步，和每一步断在哪

Ulwick 的八步法。这张表比任何功能清单都更能说明本项目的定位。

| # | 步骤 | 用户实际在做什么 | 现有方案的断点 | 本项目落点 |
|---|---|---|---|---|
| 1 | **定义** | 意识到"这步我不会 / 我可能写错了" | — | 不做（不解决动机问题） |
| 2 | **定位** | 从一沓卷子里找出那道题、那一行 | 整页照片丢进去，产品只管识别不管定位 | 部分：`tools/split_page.py` 自动切行 + 行数提示 |
| 3 | **准备** | 拍照、调光、裁到那一行 | 手抖、阴影、透视，识别率断崖 | 部分：自动摆正 → 裁到墨迹 → 放大到 640px |
| 4 | **确认** | **确认拍进去的确实是我想问的那一行** | **几乎全行业缺失**。产品默认"你传的就是你要的" | **强**：置信度 + 候选并列 + 无法解析明确标注 |
| 5 | **执行** | 得到答案 / 判定 | 题库外退化、答非所问 | 强：SymPy 精确求解 + 逐条验算 |
| 6 | **监控** | 判断这个结果可不可信 | 无信号，用户只能靠"看起来顺不顺"判断 | **强**：`verdict` + 理由列表 + 每步 `check` 结果 |
| 7 | **修正** | 改错、重问、换个写法再试 | 改一个字符要重新传图、重新识别、重新等待 | 强：点候选即重算，回车即重算，不重跑识别 |
| 8 | **收尾** | 抄进作业、记住方法、跟人解释 | 解析与步骤脱节 | 中：讲评绑定已验算步骤，禁写公式 |

### 这张表说明了什么

把用户的注意力分布画出来，会看到一条明显的错位：

```
现有产品重心：   ████░░░░░░░░░░░░░░░░  ← 全压在 5（执行）
用户真正的痛点： ░░░░░░████████████░░  ← 集中在 4 / 6 / 7
本项目的重心：   ░░░░░░████████████░░  ← 主动对齐用户
```

**执行（第 5 步）是最容易做、最容易演示、也最拥挤的一段。**

而第 4、6、7 步——确认输入对不对、判断输出可不可信、低成本地改一改再试——才是用户真正反复卡住的地方。这三步有个共同点：**它们都要求系统对自己的状态有感知**。

这就是为什么本项目要花大力气在"验算"上：不是为了让答案更准，是为了让系统能回答"我这个答案有多可信"。

几何引擎里那条规矩最能体现这一点：

> 任何规则或作图给出的结论，先在解出的坐标上量一遍，对不上整条丢弃。

这条规矩不提高识别率，也不提高解题能力。它唯一的用途是让系统在说"这个结论成立"时，这句话是有据的。这是第 6 步的工程。

## 5. 期望结果（Desired Outcomes）

用 Ulwick 的格式：`[方向] + [度量] + [对象] + [情境限定]`。**每条都不含解决方案**——写"要有置信度条"是功能，写"最小化用户拿到错误结论的概率"才是结果。

标记：✅ 已可量化 / 🟡 部分覆盖 / ⬜ 未覆盖

### J2 · 判定（信任枢纽，优先级最高）

| # | 期望结果 | 覆盖 | 对应指标 |
|---|---|---|---|
| O1 | 最小化「系统给出确定结论但结论错误」的概率 | ✅ | 端到端正确率 × (1 − 幻觉率) |
| O2 | 最小化「系统不确定却没有表达出来」的概率 | 🟡 | 人工干预率需与准确率同看 |
| O3 | 最大化「系统标注为需确认的样本中，确实存在问题」的比例 | 🟡 | 干预后准确率反推 |
| O4 | 最小化用户从「看到结果」到「判断可不可信」所需的时间 | 🟡 | 理由条数 ≤ 3，需实测阅读时长 |
| O5 | 最小化「同一份输入两次运行给出不同结论」的概率 | ✅ | 多解投票一致度 |
| O6 | 最小化「结论正确但用户不信」的概率 | ⬜ | 需用户调研，无法从日志得到 |

**O6 值得单独说。**

它是唯一一条**无法用现有指标度量**的结果，也是最容易被工程师忽略的。系统可以说"这题解是 x=2"，同时用户心里想"你怎么知道的"。

本项目的对策是把依据摆在结论旁边：理由列表、候选并列、每步的验算结论。但这是不是真的提升了信任，只能问用户。**这条要写进报告的"未验证假设"。**

### J1 · 转录

| # | 期望结果 | 覆盖 | 对应指标 |
|---|---|---|---|
| O7 | 最大化「输出与纸上语义等价」的比例 | ✅ | 语义等价率（不是 ExpRate） |
| O8 | 最小化「认错了但系统以为认对了」的概率 | ✅ | 无法解析候选的显式标注 |
| O9 | 最小化「修正一个字符所需的用户动作数」 | ✅ | 点选 = 1 次，改文本框 = 重输 |
| O10 | 最小化「排版差异被误判为错误」的概率 | ✅ | 语义等价率与 ExpRate 的差值 |

**O10 是被低估的一条。**

`\frac{1}{2}x` 和 `\frac{x}{2}` 在手写里是同一个东西，字符串却不同。用 ExpRate 评，系统会被判错，用户会觉得"这都认不出来"。

两个指标都报，差值本身是发现——这个做法在 JTBD 里的依据就是 O10：用户判定的标准是"意思对不对"，不是"字符一不一样"。

### J3 · 讲通

| # | 期望结果 | 覆盖 | 对应指标 |
|---|---|---|---|
| O11 | 最小化「讲解中出现用户无法核对的说法」的概率 | ✅ | 幻觉率（被后置校验剔除的步骤占比） |
| O12 | 最小化「讲解与已验算步骤矛盾」的概率 | ✅ | 回扫：出现无法溯源的等式整段作废 |
| O13 | 最大化「用户能用自己的话复述思路」的比例 | ⬜ | 需用户调研 |
| O14 | 最小化「答案正确但过程被讲错」的概率 | 🟡 | `ok=False` 时不生成讲评 |

**O14 对应一条反直觉的设计决策：算错的时候，宁可不讲。**

`pipeline.py` 里 `sr.ok=False` 直接跳过讲评生成。理由写得很直白——**算错的时候讲得越顺，害处越大**。

多数产品会把"讲解"当成兜底体验：答不出就多讲两句，显得没白来。但从 JTBD 看，J3 的失败代价是"学错方法"，而一个错误答案配上流畅讲解，恰好是最容易让人学错的形式。

## 6. 竞争地图：用户此刻还能雇谁

JTBD 的核心方法论之一：**竞争者不是同类产品，是用户此刻实际会用的所有替代方案**，包括"什么都不做"。

| 替代方案 | J1 转录 | J2 判定 | J3 讲通 | 用户为什么还是用它 |
|---|---|---|---|---|
| 作业帮 / 小猿搜题 | 强 | **弱** | 中 | 快、免费、原题有解析 |
| 通用大模型（拍照问） | 中 | **弱** | **强（但可能错）** | 什么都能问，讲得比解析好懂 |
| 公式 OCR（SimpleTex / Mathpix） | **强** | 无 | 无 | 转 LaTeX 准，但不管对错 |
| 问老师 | 无 | **最强** | **最强** | 可信度天花板，但要等到明天 |
| 问同学 | 弱 | 弱 | 弱 | 零心理成本，随时能问 |
| 自己硬啃 | 无 | 无 | 无 | 不用开口，但要耗时间 |
| **抄一份交上去** | 无 | 无 | 无 | **成本最低** |
| **放弃这题** | 无 | 无 | 无 | 零成本 |

### 两个真正的对手

**对手一：抄一份交上去。**

这是 JTBD 视角下最诚实的发现。当学生判断"搞懂它"的成本高于"被抓的概率 × 被抓的代价"时，最理性的选择是抄。

任何解题产品在这个对手面前都很弱，因为抄不需要理解。**唯一能赢的角度是降低"搞懂"的成本**——不是给更详细的解析，是让"确认我这一步对不对"这个动作本身变得极便宜。

这正是第 7 步（修正）要优化的东西：点一下候选就重算，而不是重传一遍图。

**对手二：问同学。**

零心理成本。E2 说"不想显得自己很笨"——问 AI 之所以有机会，是因为它不知道你是谁。但一旦 AI 开始反问"你说的 x 是字母还是乘号"，这个优势就被削掉一半。

所以追问的设计必须克制：**只在真的分岔时问，问的时候给选项而不是让用户描述。** 29% 的干预率是刻意压过的结果，不是自然产物。

### 本项目的竞争位置

```
              可信度 高
                  ▲
        问老师    │        ★ 本项目（限定域内）
                  │
        公式OCR   │   通用大模型
                  │
    ──────────────┼──────────────► 覆盖广度
                  │
        问同学    │   作业帮/小猿
                  │
              可信度 低
```

本项目用**覆盖广度**换**可信度**，在窄域里把可信度做到接近"问老师"的水平——代价是超出范围就明确拒答。

这不是能力不足的妥协，是任务定义的必然结果：**J2 这个任务没法用"大概对"来完成。**

## 7. 从 JTBD 反推设计：每个决策服务哪条任务

这张表是本文档最实用的部分。它回答"如果砍掉某个设计，会伤到哪条 job"。

| 设计决策 | 服务任务 | 砍掉的后果 |
|---|---|---|
| 多源识别（SimpleTex + Qwen3-VL）而非单模型 | F1 / O7 | 两源架构不同，错误模式才不相关；单源时投票没有意义 |
| 语义聚类投票（`simplify(a-b)==0`）而非字符串相等 | O10 | 排版差异被误判为错误，用户觉得"这都认不出" |
| 低置信时降级 `review` 而不是硬给答案 | E1 / O2 | 系统会开始骗人，而骗人的系统一旦被识破就彻底失去价值 |
| 解析失败返回 `ok=False` 而非抛异常 | 可排查性 | "识别错"和"解析器崩"混在一起，永远查不清是谁的问题 |
| 每条步骤带 `check` 模式，事后逐条复算 | F3 / O1 | 步骤从"可验算的推导"退化成"文案" |
| 增根剔除（代回分母检验） | F2 | 给出数学上无效的解，且用户不易察觉 |
| `ok=False` 时不生成讲评 | O14 | 错误答案配流畅讲解，是最容易让人学错的形式 |
| 讲评禁写公式 + 输出后回扫 | O11 / O12 | 大模型会在讲解里塞进自己编的等式 |
| 几何题作图结论先在坐标上量一遍 | 第 6 步 / O1 | 规则推出的结论无据，等于凭空断言 |
| 超范围直接 `out_of_scope(reason)` | F6 / S1 | 硬撑出的答案学生复述不出来，在老师面前露馅 |
| 点选候选即重算，不重跑识别 | O9 / 第 7 步 | 改一个字符要等一整套流程，用户会放弃修正直接抄 |
| 图片按 SHA256 缓存 | E4 | 调试期反复计费，迭代速度下降 |

**一句话读这张表：**

除了前两条是识别质量，后面十条全部服务于"让系统对自己的状态诚实"。这不是技术偏好，是项目选定的任务要求。

## 8. 这个项目自己也要完成一个 job

JTBD 不只用于分析终端用户。这个项目作为一件交付物，也在被"雇佣"。

### 8.1 作者的 job

> 当我要用一个结课项目证明自己真的做过工程判断时，我想让评审在十分钟内看到"这个人知道自己在解决哪个问题、边界在哪、怎么验证"；这样我拿到的评价不止是"跑通了"，而是"想清楚了"。

这个 job 直接决定了文档的形态：

| 要满足 | 对应产物 | 为什么不能省 |
|---|---|---|
| 让人相信边界是主动划的，不是做不到 | 范围表 + 「明确不做」清单 | 没有边界声明的项目，看起来像没做完 |
| 让人相信指标不是挑好看的报 | 同时报 ExpRate 与语义等价率，并解释差值 | 只报一个指标，评审会怀疑另一个很难看 |
| 让人相信失败案例是设计的一部分 | 29% 干预率写成"设计目标"而非"缺陷" | 把缺陷讲成设计，是最容易被识破的话术；把设计讲成缺陷，反而可信 |
| 让人能自己验证 | `pytest` 96 项、`demo.py` 7 例、无需密钥可跑 | 评审不会装环境，能一条命令跑起来就是可信度 |

### 8.2 这份 JTBD 本身的 job

> 当评审读技术文档觉得"功能挺多但不知道为什么要这么做"时，我想看到一套把功能和任务对上号的推理；这样我能判断这些功能是长出来的，还是堆上去的。

所以第 7 节那张表是本文档的核心，其余部分是它的前提。

### 8.3 一个诚实的位置说明

本项目在真实市场上并不构成对作业帮的替代——覆盖广度差太远，且依赖单机部署。

它的价值在于**证明"限定域可信"这条路线可行且可量化**：在一万道题上做到 60% 覆盖率 + 95% 可信度，与在无穷题上做到 40% 覆盖率 + 60% 可信度，是两种不同的产品哲学。

前者是本题目的答案。

## 9. 如果只能记住三件事

**第一，行业偷换了任务。**
用户提交的是"帮我判对错"，产品交付的是"给你标准答案，你自己比"。这两件事在少数情况下重合，在大多数情况下不重合——尤其是学生自己写错、或者题库里没有的时候，而这两类恰好是用户最需要帮助的时候。

**第二，答案的可信度是产品，不是指标。**
29% 的人工干预率看起来是缺陷，实际是产品在履行"不确定就说"这个承诺。真正要压的不是这个数字，是"剩下 71% 里有多少本该问却没问"。

**第三，本项目的全部工程重心在 Job Map 的第 4、6、7 步。**
确认输入、监控可信度、低成本修正。这三步有一个共同前提：系统要对自己的状态有感知。所以验算不是锦上添花，它是这个产品的本体。
